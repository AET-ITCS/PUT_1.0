# 项目内部统一协议帧格式

> 本文描述本项目自定义的大核 Linux → 小核 RTOS 内部统一转发协议。

## 1. 协议定位

本项目外部输入来自：

```text
4G / WiFi / 蓝牙 / 以太网 / RS485 / MQTT 或云端数据
```

当前业务中，外部数据不会直接是 anyMSG。因此主流程为：

```text
外部协议数据
    ↓
大核 Linux 对应 parser 解析
    ↓
提取业务命令并映射 CAN ID / CAN DATA
    ↓
封装为 unified_frame_t
    ↓
大小核通信
    ↓
小核 RTOS 解析 unified_frame_t
    ↓
发送官方 CAN / CAN FD 报文
```

也就是说：

```text
外部协议 → unified_frame_t → CAN
```

不是：

```text
外部协议 → anyMSG → unified_frame_t → CAN
```

`unified_frame_t` 的作用是让小核不关心数据最初来自 4G、WiFi、蓝牙、以太网、RS485 还是 MQTT。小核只识别一种内部帧，然后按其中的 `can_id / can_dlc / can_data` 发送 CAN。

## 2. 协议基本参数

| 项目 | 值 | 说明 |
|---|---:|---|
| 协议名称 | `unified_frame_t` | 项目内部统一转发帧 |
| 使用位置 | 大核 Linux → 小核 RTOS | 大小核通信载荷 |
| 帧长度 | 96 字节 | 固定长度，便于小核解析 |
| 帧头 | `0xA55A` | 用于快速判断帧起始/合法性 |
| 协议版本 | `0x01` | 当前版本 |
| 数据区长度 | 64 字节 | 兼容 CAN FD；普通 CAN 只使用前 8 字节 |
| 校验 | CRC16 | 覆盖除 `crc16` 字段外的前 94 字节 |
| 字节序 | little-endian | 多字节整数按小端存储 |

## 3. 帧结构

当前 C 定义位于：

```text
common/include/unified_frame.h
```

结构如下：

```c
typedef struct __attribute__((packed)) {
    uint16_t magic;
    uint8_t  version;
    uint8_t  frame_type;
    uint8_t  source_protocol;
    uint8_t  vehicle_type;
    uint8_t  can_dlc;
    uint8_t  can_flags;
    uint32_t sequence;
    uint32_t timestamp_ms;
    uint32_t source_id;
    uint32_t destination_id;
    uint32_t can_id;
    uint8_t  reserved[2];
    uint8_t  can_data[64];
    uint16_t crc16;
} unified_frame_t;
```

### 3.1 字段布局

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---:|---:|---|---|---|
| 0 | 2 | `magic` | `uint16_t` | 固定 `0xA55A` |
| 2 | 1 | `version` | `uint8_t` | 当前固定 `0x01` |
| 3 | 1 | `frame_type` | `uint8_t` | 内部帧类型 |
| 4 | 1 | `source_protocol` | `uint8_t` | 外部来源协议 |
| 5 | 1 | `vehicle_type` | `uint8_t` | 车身业务类型 |
| 6 | 1 | `can_dlc` | `uint8_t` | CAN 数据字节数 |
| 7 | 1 | `can_flags` | `uint8_t` | CAN 标志位 bitmask |
| 8 | 4 | `sequence` | `uint32_t` | 帧序号，由大核递增生成 |
| 12 | 4 | `timestamp_ms` | `uint32_t` | 大核时间戳，单位 ms |
| 16 | 4 | `source_id` | `uint32_t` | 逻辑来源 ID，由协议适配层生成 |
| 20 | 4 | `destination_id` | `uint32_t` | 逻辑目的 ID，由协议适配层生成 |
| 24 | 4 | `can_id` | `uint32_t` | 要发送的 CAN 标准 ID 或扩展 ID |
| 28 | 2 | `reserved` | `uint8_t[2]` | 保留字段，当前填 0 |
| 30 | 64 | `can_data` | `uint8_t[64]` | CAN / CAN FD 数据区 |
| 94 | 2 | `crc16` | `uint16_t` | CRC16 校验值 |

总长度：

```text
2 + 1 + 1 + 1 + 1 + 1 + 1 + 4 + 4 + 4 + 4 + 4 + 2 + 64 + 2 = 96 字节
```

## 4. 枚举定义

### 4.1 来源协议 `source_protocol`

| 值 | 名称 | 含义 |
|---:|---|---|
| `0x00` | `PROTOCOL_TYPE_UNKNOWN` | 未知来源 |
| `0x01` | `PROTOCOL_TYPE_4G` | 4G 数据 |
| `0x02` | `PROTOCOL_TYPE_WIFI` | WiFi 数据 |
| `0x03` | `PROTOCOL_TYPE_BLUETOOTH` | 蓝牙数据 |
| `0x04` | `PROTOCOL_TYPE_ETHERNET` | 以太网数据 |
| `0x05` | `PROTOCOL_TYPE_RS485` | RS485 数据 |
| `0x06` | `PROTOCOL_TYPE_CLOUD_MQTT` | MQTT / 云端数据 |

### 4.2 车身业务类型 `vehicle_type`

这些数值参考老师资料中的业务 type，但本项目不要求先转 anyMSG。

| 值 | 名称 | 含义 |
|---:|---|---|
| `0x47` | `VEHICLE_MSG_TYPE_SEAT_CONTROL` | 座椅控制 |
| `0x48` | `VEHICLE_MSG_TYPE_SEAT_FEEDBACK` | 座椅反馈 |
| `0x49` | `VEHICLE_MSG_TYPE_LIGHT_CONTROL` | 灯光控制 |
| `0x50` | `VEHICLE_MSG_TYPE_LIGHT_FEEDBACK` | 灯光反馈 |
| `0x51` | `VEHICLE_MSG_TYPE_WINDOW_CONTROL` | 车窗控制 |
| `0x52` | `VEHICLE_MSG_TYPE_WINDOW_FEEDBACK` | 车窗反馈 |

### 4.3 内部帧类型 `frame_type`

| 值 | 名称 | 含义 |
|---:|---|---|
| `0x01` | `UNIFIED_FRAME_TYPE_CAN_DATA` | CAN 数据帧，下发给小核发送 CAN |
| `0x02` | `UNIFIED_FRAME_TYPE_STATUS` | 状态帧，预留给小核回传状态 |
| `0x03` | `UNIFIED_FRAME_TYPE_HEARTBEAT` | 心跳帧，预留给大小核保活 |
| `0x04` | `UNIFIED_FRAME_TYPE_ERROR` | 错误帧，预留给异常上报 |

当前主流程优先实现 `UNIFIED_FRAME_TYPE_CAN_DATA`。

### 4.4 CAN 标志位 `can_flags`

`can_flags` 是 bitmask，可以组合使用。

| bit | 值 | 名称 | 含义 |
|---:|---:|---|---|
| - | `0x00` | `UNIFIED_CAN_FLAG_NONE` | 普通 CAN 标准数据帧 |
| 0 | `0x01` | `UNIFIED_CAN_FLAG_EXTENDED_ID` | 使用 29-bit 扩展 ID |
| 1 | `0x02` | `UNIFIED_CAN_FLAG_FD` | 使用 CAN FD，允许 `can_dlc <= 64` |
| 2 | `0x04` | `UNIFIED_CAN_FLAG_RTR` | 远程帧，预留 |
| 3 | `0x08` | `UNIFIED_CAN_FLAG_BRS` | CAN FD Bit Rate Switch，预留 |

## 5. 字段含义说明

### 5.1 `magic`

固定为：

```text
0xA55A
```

小核收到数据后先检查该字段。如果不是 `0xA55A`，直接丢弃。

### 5.2 `version`

当前固定为：

```text
0x01
```

后续如果帧结构发生不兼容变化，需要提升版本号。

### 5.3 `source_protocol`

用于记录数据最初来自哪一路外部协议。

例如：

```text
RS485 收到数据       → source_protocol = 0x05
WiFi 收到数据        → source_protocol = 0x02
MQTT/云端收到数据    → source_protocol = 0x06
```

小核一般不需要根据该字段做复杂业务判断，但它对调试、日志和回传状态有用。

### 5.4 `vehicle_type`

表示当前业务类型，例如座椅控制、灯光控制、车窗控制。

大核 parser 负责从外部协议中提取业务含义，然后填入该字段。

### 5.5 `source_id` / `destination_id`

这是项目内部逻辑 ID，不再使用 anyMSG 的 `source_cid / destination_cid`。

推荐用法：

| 字段 | 建议含义 |
|---|---|
| `source_id` | 来源设备、通道、客户端或任务 ID |
| `destination_id` | 目标设备、目标节点或目标功能 ID |

如果当前协议暂时没有明确来源/目的，可先填 0。

### 5.6 `can_id`

小核最终发送 CAN 时使用的 CAN ID。

- 标准帧：使用 11-bit ID，范围 `0x000 ~ 0x7FF`。
- 扩展帧：使用 29-bit ID，范围 `0x00000000 ~ 0x1FFFFFFF`，同时设置 `UNIFIED_CAN_FLAG_EXTENDED_ID`。

### 5.7 `can_dlc`

本项目内部直接表示 CAN 数据字节数：

| 类型 | 条件 | 合法范围 |
|---|---|---|
| 普通 CAN | `can_flags` 不包含 `UNIFIED_CAN_FLAG_FD` | `0 ~ 8` |
| CAN FD | `can_flags` 包含 `UNIFIED_CAN_FLAG_FD` | `0 ~ 64` |

### 5.8 `can_data`

`can_data` 是小核最终要发送到 CAN 总线的数据区。

- 普通 CAN 只使用 `can_data[0] ~ can_data[can_dlc - 1]`，且 `can_dlc <= 8`。
- CAN FD 可使用最多 64 字节。
- 未使用的字节建议填 0。

## 6. 校验规则

### 6.1 小核接收检查顺序

小核收到一帧后建议按以下顺序检查：

```text
1. 检查长度是否为 96 字节
2. 检查 magic 是否为 0xA55A
3. 检查 version 是否支持
4. 检查 frame_type 是否合法
5. 检查 source_protocol 是否合法
6. 检查 vehicle_type 是否合法
7. 检查 can_dlc 是否符合 can_flags
8. 计算 CRC16 并和 crc16 字段比较
9. 检查通过后发送 CAN
```

### 6.2 CRC16

当前协议约定：

```text
算法：CRC-16/CCITT-FALSE
多项式：0x1021
初值：0xFFFF
输入反转：false
输出反转：false
结果异或：0x0000
覆盖范围：unified_frame_t 前 94 字节，即不包含 crc16 字段本身
```

## 7. 典型工作流程

### 7.1 RS485 转 CAN 示例

```text
RS485 收到原始数据
    ↓
rs485_modbus.c 解析业务命令
    ↓
得到：座椅控制 / 座椅 3 / 下移 16mm / 前移 21mm / 角度调大 9°
    ↓
frame_packer.c 映射 CAN ID 和 CAN DATA
    ↓
生成 unified_frame_t
    ↓
ipc_to_rtos.c 发送给小核
    ↓
小核发送 CAN
```

示例内部帧字段可以是：

| 字段 | 示例值 | 说明 |
|---|---:|---|
| `magic` | `0xA55A` | 固定帧头 |
| `version` | `0x01` | 当前版本 |
| `frame_type` | `0x01` | CAN 数据帧 |
| `source_protocol` | `0x05` | RS485 |
| `vehicle_type` | `0x47` | 座椅控制 |
| `can_flags` | `0x00` | 普通 CAN 标准帧 |
| `can_id` | `0x123` | 示例 CAN ID，后续按实际车身映射表确定 |
| `can_dlc` | `8` | 发送 8 字节 |
| `can_data` | `21 24 10 15 09 00 00 00` | 示例座椅控制数据 |

> 注意：上面的 `can_id = 0x123` 只是示例，最终 CAN ID 需要根据实际车身 CAN 映射表确定。

### 7.2 WiFi / MQTT 转 CAN 示例

```text
WiFi 或 MQTT 收到控制 JSON / 私有帧
    ↓
对应 parser 解析业务含义
    ↓
转换为 unified_frame_t
    ↓
小核发送 CAN
```

这里不需要构造 anyMSG。

## 8. 错误处理

公共错误码位于：

```text
common/include/error_code.h
```

常用错误码：

| 错误码 | 含义 |
|---:|---|
| `0` | 成功 |
| `-1` | 空指针 |
| `-2` | 参数非法 |
| `-3` | 长度错误 |
| `-10` | 协议头错误 |
| `-11` | payload 长度错误 |
| `-12` | 未知业务类型 |
| `-13` | CRC 错误 |
| `-20` | CAN DLC 越界 |
| `-30` | 环形缓冲区空 |
| `-31` | 环形缓冲区满 |

## 9. 和 anyMSG 的关系

老师给的 anyMSG 资料对本项目仍有参考价值，主要包括：

- 车身业务类型：`0x47 ~ 0x52`。
- 座椅、灯光、车窗控制 payload 的业务语义。
- 滚动码、校验码等安全设计思路。

但当前主流程中：

```text
不接收 anyMSG
不生成 anyMSG
不解析 anyMSG
不把 anyMSG 发送给小核
```

本项目真正的内部统一协议是：

```text
unified_frame_t
```
