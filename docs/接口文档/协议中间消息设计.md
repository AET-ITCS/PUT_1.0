# 协议中间消息设计

## 1. 设计目的

`protocol_parsed_msg_t` 是大核 Linux 协议转换层内部使用的 **协议中间消息**。

它位于外部协议解析和统一帧打包之间：

```text
外部协议原始数据
  ↓
各协议 parser
  ↓
protocol_parsed_msg_t
  ↓
frame_packer_pack
  ↓
unified_frame_t
  ↓
ipc_to_rtos_send
```

设计这个中间结构的目的，是把两类职责分开：

```text
协议模块：负责解析“外部数据表达了什么业务含义”
打包模块：负责把“业务含义”封装成大核到小核统一帧
```

这样每个协议模块不需要重复处理 `unified_frame_t` 的公共字段、序号、时间戳和 CRC。

---

## 2. 为什么不让每个协议直接生成 unified_frame_t

从功能上说，外部协议模块可以直接生成 `unified_frame_t`。

但项目里有多种输入协议：

```text
以太网 UDP / TCP
RS485 / Modbus
WiFi
蓝牙
4G / MQTT
```

如果每个协议模块都直接生成 `unified_frame_t`，就会出现大量重复逻辑：

```text
magic 填充
version 填充
frame_type 填充
sequence 递增
timestamp_ms 获取
reserved 清零
can_dlc 校验
can_id 校验
crc16 计算
```

后期容易出现不一致，例如：

```text
以太网模块 CRC 算法正确
RS485 模块忘记清零 reserved
WiFi 模块 sequence 规则不同
蓝牙模块忘记填 version
4G 模块 can_dlc 校验不完整
```

因此本项目采用两步转换：

```text
外部协议 → protocol_parsed_msg_t → unified_frame_t
```

也就是：

```text
各协议模块只负责“解析业务结果”
frame_packer 统一负责“封装统一帧”
```

## 3. 当前结构定义

当前定义位于：

```text
linux_app/core/protocol_parsed_msg.h
```

结构如下：

```c
typedef struct {
    protocol_type_t source_protocol;
    uint8_t vehicle_type;
    uint32_t source_id;
    uint32_t destination_id;
    uint32_t can_id;
    uint8_t can_dlc;
    uint8_t can_flags;
    uint8_t can_data[UNIFIED_CAN_FD_DATA_MAX_LEN];
} protocol_parsed_msg_t;
```

---

## 4. 字段说明

| 字段 | 含义 | 由谁填写 |
|---|---|---|
| `source_protocol` | 数据来源协议，例如以太网、RS485、WiFi | 协议 parser |
| `vehicle_type` | 车身业务类型，例如座椅控制、灯光控制、车窗控制 | 协议 parser |
| `source_id` | 来源设备、通道、客户端或任务 ID | 协议 parser，可暂填 0 |
| `destination_id` | 目标设备、节点或功能 ID | 协议 parser，可暂填 0 |
| `can_id` | 小核最终要发送的 CAN ID | 协议 parser |
| `can_dlc` | CAN 数据字节数 | 协议 parser |
| `can_flags` | CAN 标志位，例如标准帧、扩展帧、CAN FD | 协议 parser |
| `can_data` | CAN / CAN FD 数据区 | 协议 parser |

该结构只保存已经解析出的业务结果，不保存外部协议自己的帧头、长度、CRC 等字段。

---

## 5. 各模块职责边界

### 5.1 协议 parser 负责

例如 `linux_app/以太网/ethernet_udp.c`：

```text
检查外部协议 magic/version/length/CRC
解析外部协议字段
提取 vehicle_type
提取 can_id
提取 can_dlc
提取 can_flags
提取 can_data
输出 protocol_parsed_msg_t
```

协议 parser 不负责：

```text
填写 unified_frame_t.magic
填写 unified_frame_t.version
生成 sequence
生成 timestamp_ms
计算 unified_frame_t.crc16
决定 unified_frame_t.frame_type
```

这些属于 `frame_packer`。

### 5.2 frame_packer 负责

`linux_app/core/frame_packer.c` 负责：

```text
检查 protocol_parsed_msg_t 是否合法
检查 source_protocol 是否合法
检查 vehicle_type 是否合法
检查 can_dlc 是否符合 can_flags
检查 can_id 是否符合标准帧 / 扩展帧范围
填写 unified_frame_t.magic
填写 unified_frame_t.version
填写 unified_frame_t.frame_type
生成 sequence
生成 timestamp_ms
拷贝 CAN 字段
清零 reserved
计算 unified_frame_t.crc16
```

## 6. 以太网 UDP 示例

以当前调试用 UDP 帧为例：

```text
UDP 原始 payload
  ↓
ethernet_udp_parse_frame()
  ↓
protocol_parsed_msg_t
```

如果 UDP 调试帧表示：

```text
vehicle_type = 0x49
can_id       = 0x123
can_dlc      = 8
can_flags    = 0x00
can_data     = 01 02 03 04 05 06 07 08
```

解析后得到：

```c
protocol_parsed_msg_t msg = {
    .source_protocol = PROTOCOL_TYPE_ETHERNET,
    .vehicle_type = VEHICLE_MSG_TYPE_LIGHT_CONTROL,
    .source_id = 0,
    .destination_id = 0,
    .can_id = 0x123,
    .can_dlc = 8,
    .can_flags = UNIFIED_CAN_FLAG_NONE,
    .can_data = {0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07, 0x08}
};
```

然后统一交给：

```c
frame_packer_pack(&msg, &frame);
```

生成 `unified_frame_t`。

## 7. 后续新增协议时怎么做

新增协议时，只需要实现：

```text
外部协议原始数据 → protocol_parsed_msg_t
```

例如：

```text
RS485 / Modbus 帧 → protocol_parsed_msg_t
TCP 私有帧       → protocol_parsed_msg_t
蓝牙自定义帧     → protocol_parsed_msg_t
4G / MQTT 数据   → protocol_parsed_msg_t
```

然后复用同一套：

```text
protocol_parsed_msg_t → frame_packer_pack → unified_frame_t
```

这样后续协议扩展时，不需要重复实现统一帧打包逻辑。

## 9. 简单总结

可以这样理解：

```text
protocol_parsed_msg_t = 各协议解析后的“统一业务结果”
unified_frame_t       = 大核发给小核的“统一传输帧”
```

二者职责不同：

```text
protocol_parsed_msg_t 关注业务语义
unified_frame_t 关注大小核传输格式
```

所以本项目保留中间消息层，而不是让每个协议模块直接生成 `unified_frame_t`。
