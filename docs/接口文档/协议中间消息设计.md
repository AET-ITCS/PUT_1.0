# 协议中间消息设计

## 1. 设计目的

`protocol_parsed_msg_t` 是大核 Linux 网关内部使用的协议中间消息，位于外部通道解析和统一帧打包之间：

```text
外部通道原始数据
  ↓
各协议 parser
  ↓
protocol_parsed_msg_t
  ↓
frame_packer_pack()
  ↓
unified_frame_t
  ↓
ipc_to_rtos_send()
```

当前 `linux_app` 定位是纯 CAN 网关：parser 只提取 CAN 字段，不解释灯光、车窗、座椅等应用层含义。

---

## 2. 为什么保留中间消息层

项目有多种输入通道：

```text
以太网 UDP / RS485 / 后续 WiFi / 蓝牙 / 4G / MQTT
```

如果每个通道都直接生成 `unified_frame_t`，就会重复实现：

```text
magic / version / frame_type 填充
sequence 递增
timestamp_ms 获取
reserved 清零
can_dlc / can_id 校验
crc16 计算
```

因此采用两步：

```text
外部通道 → protocol_parsed_msg_t → unified_frame_t
```

parser 只负责把外部 payload 里的 CAN 字段提出来；`frame_packer` 统一负责内部帧公共字段和 CRC。

---

## 3. 当前结构定义

定义位于：

```text
linux_app/core/protocol_parsed_msg.h
```

```c
typedef struct {
    protocol_type_t source_protocol;
    uint8_t vehicle_type;
    uint32_t source_id;
    uint32_t destination_id;
    uint32_t can_id;
    uint8_t can_dlc;
    uint8_t can_flags;
    uint8_t can_data[UNIFIED_CAN_FD_DATA_MAX_LEN];
} protocol_parsed_msg_t;
```

---

## 4. 字段说明

| 字段 | 含义 | 当前网关模式填写方式 |
|---|---|---|
| `source_protocol` | 数据来源通道 | UDP 填 `PROTOCOL_TYPE_ETHERNET`，RS485 填 `PROTOCOL_TYPE_RS485` |
| `vehicle_type` | 消息类型 | 固定填 `VEHICLE_MSG_TYPE_RAW_CAN` |
| `source_id` | 来源设备、通道或客户端 ID | 第一版填 `0` |
| `destination_id` | 目标设备或节点 ID | 第一版填 `0` |
| `can_id` | 小核最终要发送的 CAN ID | 从外部 CAN direct 帧提取 |
| `can_dlc` | CAN 数据字节数 | 从外部 CAN direct 帧提取 |
| `can_flags` | CAN 标志位 | 从外部 CAN direct 帧提取 |
| `can_data` | CAN / CAN FD 数据区 | 从外部 CAN direct 帧提取 |

该结构不保存外部通道自己的帧头、长度、CRC 等字段。

---

## 5. 模块职责边界

### 5.1 parser 负责

以 `can_direct_frame.c` 为例：

```text
检查外部 CAN direct 帧 magic/version/reserved/length/CRC
提取 can_id
提取 can_dlc
提取 can_flags
提取 can_data
设置 source_protocol
设置 vehicle_type = RAW_CAN
输出 protocol_parsed_msg_t
```

parser 不负责：

```text
填写 unified_frame_t.magic / version / frame_type
生成 sequence
生成 timestamp_ms
计算 unified_frame_t.crc16
调用 IPC
```

### 5.2 frame_packer 负责

`frame_packer.c` 负责：

```text
检查 source_protocol 是否合法
检查 vehicle_type 是否合法（RAW_CAN 合法）
检查 can_dlc 是否符合 can_flags
检查 can_id 是否符合标准帧 / 扩展帧范围
填写 unified_frame_t 公共字段
生成 sequence / timestamp_ms
拷贝 CAN 字段
清零 reserved
计算 unified_frame_t.crc16
```

## 6. 示例

CAN direct UDP payload 表示：

```text
can_id    = 0x123
can_dlc   = 8
can_flags = 0x00
can_data  = 01 02 03 04 05 06 07 08
```

解析后得到：

```c
protocol_parsed_msg_t msg = {
    .source_protocol = PROTOCOL_TYPE_ETHERNET,
    .vehicle_type = VEHICLE_MSG_TYPE_RAW_CAN,
    .source_id = 0,
    .destination_id = 0,
    .can_id = 0x123,
    .can_dlc = 8,
    .can_flags = UNIFIED_CAN_FLAG_NONE,
    .can_data = {0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07, 0x08}
};
```

然后统一交给：

```c
frame_packer_pack(&msg, &frame);
```

## 7. 当前相关文件

| 文件 | 作用 |
|---|---|
| `linux_app/core/protocol_parsed_msg.h` | 定义协议中间消息结构 |
| `linux_app/core/can_direct_frame.c/.h` | 解析 UDP/RS485 共用 CAN direct 网关帧 |
| `linux_app/core/frame_packer.c/.h` | 实现中间消息到统一帧的转换 |
| `linux_app/ethernet/ethernet_udp.c/.h` | UDP 入口 |
| `linux_app/rs485/rs485_debug.c/.h` | RS485 入口和字节流同步 |
| `linux_app/core/protocol_manager.c` | 串联 parser、packer、IPC 发送流程 |

---

## 8. 简单总结

```text
protocol_parsed_msg_t = 各通道解析后的统一 CAN 字段结果
unified_frame_t       = 大核发给小核的内部统一传输帧
```

当前网关模式下：

```text
protocol_parsed_msg_t 不关注应用语义
unified_frame_t 不关注外部通道格式
```
