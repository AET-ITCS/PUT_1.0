协议碎片化

CAN / RS485 / Bluetooth / 4G / Ethernet 并存，传统方案堆叠转换器，拓扑混乱、维护成本高。

实时性不可控

单核网关同时处理大吞吐 I/O 与控制帧，容易出现调度延迟和抖动，核心控制链路风险上升。

低功耗难落地

长期物理监听与超低功耗待机相互冲突，传统设计难以兼顾快速唤醒与低能耗。

我们的破局点：统一 anyMSG + AMP 双核协同 + 零拷贝 IPC，让复杂接入与实时路由彻底解耦。

PUT · 多协议统一终端动态主链路：输入 → Linux 接入 → IPC → 小核路由 → Linux 出口

这一页是总架构动态链路。数据从外部设备进入，先由 Linux 接入层解包、分片重组和校验，再写 Frame Pool 与 RX Ring。

Mailbox 只当门铃，小核 drain descriptor 后做心跳、CID 路由和优先级调度；之后写 TX Ring 或 Reclaim Ring，Linux 出口层再封包/分片/发送并释放 Frame Pool。

CID 分段寻址

目的地址首字节直接映射物理出口：0x20~0x3F → CAN，0x80~0x9F → Bluetooth。小核只读 destination_cid 查表路由，不解析 payload。

Type 只描述内部载荷语义

0x4B / 0x4C / 0x4D 是内部语义标签。出口层不会因 RAW_CAN 自动翻译普通 CAN 控制帧，当前 CAN 路径是 anyMSG-over-CAN 私有分片。

新增协议 = 新增适配器

协议差异全部在大核适配器层消化；CAN SOF/DATA、RS485 串口、Bluetooth RFCOMM、4G IP 通道都不进入小核核心。

physical_interface_adapter_t get_mtu() / decode_rx() / reassemble() encapsulate() / fragment_tx() / send()

端心跳消费

小核主动消费 type=0x00 心跳帧，维护端设备在线状态，不生成 type=0x01 响应，避免业务链路被心跳干扰。

防饥饿配额

优先级越高配额越大；低优先级仍保留最低通道，防止高频控制帧把状态日志完全饿死。

Fail-safe 恢复

Epoch 不匹配立即丢弃并 Reclaim；CAN Bus‑Off 由 Linux SocketCAN 错误帧监控并自恢复，接口 Offline 不阻塞其他通道。
