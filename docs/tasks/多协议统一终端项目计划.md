# 多协议 anyMSG 统一终端项目计划

## 一、项目定位

本项目面向“多协议车载/工业智能网关”设计赛，基于 **Milk-V Duo 256M** 作为主控平台，设计一款能够统一接入 CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485 六类物理接口，并在这些接口之间转发完整 **anyMSG** 业务帧的多协议统一终端。

项目核心目标是：以 `docs/设计文档/统一数据帧设计.md` 中定义的 anyMSG 作为统一业务帧，以 `docs/设计文档/整体架构设计.md` 中定义的 Linux + FreeRTOS + 共享内存 v2 架构作为主通信链路，实现多物理接口接入、分片重组、共享内存路由调度、出口封包发送、Web 可视化监控和 C51 低功耗管理。

CAN 仍然是重要演示接口和工业现场接口，但不再是唯一最终出口。目标架构中，CAN 与 Ethernet、Wi-Fi、Bluetooth、4G、RS485 一样，都是 anyMSG 的物理承载接口。

整体主链路如下：

```text
外部设备
  ↓ 完整 anyMSG 放入物理协议载荷，必要时分片
Linux 大核接入层
  ↓ 解包 / 重组 / 校验出完整 anyMSG
共享内存 RX Ring + Frame Pool
  ↓ Mailbox Doorbell 唤醒
FreeRTOS 小核路由调度
  ↓ anyMSG 头部校验 / 心跳消费 / 路由 / 优先级调度
共享内存 TX Ring + Frame Pool
  ↓ Mailbox Doorbell 通知
Linux 大核出口层
  ↓ 按目标物理接口封包 / 分片 / 发送
目标设备

Linux 侧周期生成状态快照和日志
  ↓
Rust Web 后端只读展示状态、资源、路由统计和异常事件

C51 低功耗控制单元
  ↓
负责上电、唤醒、低功耗和状态指示
```

## 二、项目整体逻辑

本项目采用 “Linux 物理收发 + 共享内存 v2 + FreeRTOS 路由调度 + Web 监控 + C51 低功耗” 的系统架构。

### 1. Linux 大核：物理接入与出口层

Milk-V Duo 256M 的大核运行 Linux，负责所有真实物理接口的接入、出口和协议差异处理。

Linux 接入层主要负责：

- CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485 六类接口监听；
- 从物理协议载荷中解出 anyMSG；
- 对低 MTU 或流式接口执行分片重组；
- 校验完整 anyMSG 的基础合法性；
- 分配 Frame Pool buffer；
- 写入对应物理接口的 RX Ring 描述符；
- 设置 RX Pending Bitmap 并通过 Mailbox Doorbell 唤醒小核；
- 维护各接口连通性、收发计数、重组错误和日志。

Linux 出口层主要负责：

- 接收小核通过 TX Ring 写出的路由结果；
- 根据 TX Pending Bitmap 唤醒对应出口执行单元；
- 从 Frame Pool 读取完整 anyMSG；
- 按目标接口执行封包、必要时分片；
- 通过 CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485 真实发送；
- 发送完成或失败后释放 Frame Pool 资源并更新统计。

Linux 不负责小核内的路由调度决策，小核完成路由后，Linux 出口层只按目标接口真实发送。

### 2. FreeRTOS 小核：anyMSG 路由调度层

小核运行 FreeRTOS，负责共享内存中的完整 anyMSG 路由、队列调度和实时控制。

小核主要负责：

- 接收 Mailbox Doorbell；
- drain 六路 RX Ring；
- 读取描述符并定位 Frame Pool 中的完整 anyMSG；
- 校验 `msg_length`、`payload_length`、CID、`type`、TTL、epoch 和描述符 CRC；
- 消费端到网关心跳等本地控制帧；
- 根据 `destination_cid` 查询目标物理接口；
- 按 priority 0/1/2/3 执行优先级调度和防饥饿配额；
- 写入目标物理接口 TX Ring；
- 设置 TX Pending Bitmap 并通知 Linux 出口层；
- 记录 no route、TTL 过期、非法 CID、非法长度、队列满等丢弃原因。

小核不直接操作 CAN 控制器，不处理 UART、网卡、蓝牙、4G 模块，也不解析 Modbus、UDS、J1939、CANopen 等复杂业务语义。小核只面对共享内存中的完整 anyMSG 和描述符元数据。

### 3. 共享内存 IPC：唯一业务数据通道

大小核之间的业务数据只通过共享内存传递。Mailbox 只作为 Doorbell 使用，不承载完整数据帧。

共享内存 v2 由以下部分组成：

- Frame Pool：保存完整 anyMSG 字节；
- Descriptor RX Ring：Linux 写，小核读；
- Descriptor TX Ring：小核写，Linux 读；
- RX/TX Pending Bitmap：表示哪些 Ring 非空；
- stats / event area：记录水位、错误、丢弃和事件；
- Mailbox Doorbell：只负责唤醒对端。

共享内存层不解释具体业务 payload，也不负责物理协议封包。

### 4. Web：只读监控展示层

Web 模块运行在 Linux 侧，面向比赛演示、现场联调和后续运维查看。后端使用 Rust + Axum/Tokio，并按 `riscv64gc-unknown-linux-musl` 静态交叉编译为 `put-webd` 单个可执行程序；前端使用 Vue3 + Vite，构建后的 `dist/` 作为外置静态文件由后端托管。

Web 模块不参与主通信链路，不直接访问共享内存，不向小核发送控制命令。数据来源采用只读方式：

- 系统资源、设备存在性和日志文件由 Web 后端直接读取；
- 接口状态、共享内存状态、路由统计和异常事件由 `linux_app` 周期写入 `/run/put/status/`；
- 系统日志、协议适配器日志和 IPC 异常日志写入 `/var/log/put/`。

Web 模块主要展示：

- CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485、大小核通信的连通性；
- 每个接口的接收计数、发送计数、错误计数、最近通信时间；
- 分片重组错误、Frame Pool 水位、RX/TX Ring 水位；
- 小核路由计数、优先级队列状态和丢弃原因；
- CPU、内存、磁盘、网络、系统运行时间等资源占用；
- 大核应用日志、协议适配器日志、IPC 异常日志和系统启动日志；
- 模块断连、CRC 错误、IPC 超时、Frame Pool 满、接口离线等异常告警。

### 5. C51：低功耗唤醒层

C51 单片机作为独立低功耗管理单元。

C51 主要负责：

- 主控上电和唤醒控制；
- 外部唤醒信号检测；
- 空闲状态下的低功耗控制；
- 部分外设电源控制；
- LED 状态指示。

C51 不参与协议转换、共享内存通信、路由调度或物理接口发送。

## 三、系统功能规划

### 1. CAN 接口 anyMSG 适配

CAN 接口作为工业现场和车载场景的重要接口，可作为 anyMSG 入口，也可作为 anyMSG 出口。

主要功能：

- 使用 CAN raw socket 或底层 CAN 驱动完成真实收发；
- 接入侧从 CAN 承载格式中重组完整 anyMSG；
- 出口侧根据 CAN MTU 执行封包和必要分片；
- 支持 RAW_CAN、CAN_FD、CAN_ISOTP、UDS、J1939、CANopen 等 payload 类型的承载；
- 记录 CAN 接口收发、分片、CRC 错误、发送失败和离线状态。

典型数据流：

```text
CAN 设备
  ↓ CAN 承载 anyMSG / 分片
Linux CAN Adapter
  ↓ decode / reassemble
完整 anyMSG
  ↓ RX Ring + Frame Pool
FreeRTOS Router Scheduler
  ↓ TX Ring + Frame Pool
Linux 目标接口 Adapter
  ↓ encapsulate / fragment_tx / send
目标设备
```

### 2. Ethernet 接口 anyMSG 适配

Ethernet 接口用于局域网调试、上位机通信和高吞吐数据承载。

主要功能：

- 支持 TCP/UDP 接入；
- 接收 PC 或上位机发送的完整 anyMSG 或分片；
- 适配器负责 decode、reassemble、encapsulate 和 send；
- 支持通过 `destination_cid` 路由到任一目标物理接口；
- 作为 Web 访问网络时，Web 只读服务与业务数据链路保持隔离。

典型数据流：

```text
PC 上位机
  ↓ TCP / UDP 承载 anyMSG
Linux Ethernet Adapter
  ↓ 完整 anyMSG
共享内存 RX Ring + Frame Pool
  ↓
FreeRTOS 小核路由调度
  ↓
目标接口 TX Ring + Linux 出口发送
```

### 3. Wi-Fi 接口 anyMSG 适配

Wi-Fi 接口使用 USB 蓝牙/Wi-Fi 二合一模块中的 Wi-Fi 功能，适合无线局域网演示和移动调试。

主要功能：

- Wi-Fi 联网和连接状态检测；
- 支持 TCP/UDP 载荷中的 anyMSG；
- 接入侧执行完整帧校验和分片重组；
- 出口侧按目标链路 MTU 决定是否分片；
- 记录无线链路断连、重连、收发计数和异常事件。

典型应用场景：

```text
手机 / PC
  ↓ Wi-Fi TCP / UDP
Linux Wi-Fi Adapter
  ↓ decode / reassemble complete anyMSG
FreeRTOS 路由调度
  ↓
CAN / Ethernet / Bluetooth / 4G / RS485 任一目标接口
```

### 4. Bluetooth 接口 anyMSG 适配

Bluetooth 接口用于手机端或近距离无线设备接入，可通过 RFCOMM 或其他蓝牙数据通道承载 anyMSG。

主要功能：

- 蓝牙模块识别、配对和连接状态检测；
- 蓝牙数据流分帧；
- 接入侧从流式数据中重组完整 anyMSG；
- 出口侧封包并发送到蓝牙连接端；
- 记录断连、重组超时、重复片和 CRC 错误。

典型数据流：

```text
手机蓝牙
  ↓ 蓝牙数据通道承载 anyMSG
Linux Bluetooth Adapter
  ↓ 流式分帧 / 重组
完整 anyMSG
  ↓
共享内存 + FreeRTOS 路由调度
  ↓
目标物理接口发送
```

### 5. 4G 接口 anyMSG 适配

4G 接口用于远程网络接入、云端连接和广域网演示。

主要功能：

- USB 4G 模块识别、拨号和联网；
- 支持 TCP/MQTT 等上层通道承载 anyMSG；
- 接入侧执行鉴权、解包、重组和基础合法性校验；
- 出口侧可将路由后的 anyMSG 发送回云端或远端服务；
- 记录网络断连、重连、发送失败、重放或鉴权失败等事件。

典型数据流：

```text
云端服务器 / MQTT / TCP
  ↓ 4G 网络承载 anyMSG
Linux 4G Adapter
  ↓ decode / reassemble / validate
共享内存 RX Ring + Frame Pool
  ↓
FreeRTOS Router Scheduler
  ↓
目标接口出口发送
```

### 6. RS485 接口 anyMSG 适配

RS485 接口用于工业现场串口总线接入，可通过私有串口封装承载 anyMSG。

主要功能：

- 串口参数配置和收发；
- 流式数据分帧；
- 接入侧重组完整 anyMSG；
- 出口侧根据串口链路能力执行分片发送；
- 记录串口错误、重组超时、丢片、重复片和发送失败。

典型数据流：

```text
RS485 设备
  ↓ RS485 帧 / 流式载荷承载 anyMSG
Linux RS485 Adapter
  ↓ decode / reassemble
完整 anyMSG
  ↓
共享内存 + FreeRTOS 路由调度
  ↓
目标接口发送
```

### 7. Web 监控展示

在 Linux 侧运行 Rust Web 后端服务，用户通过浏览器访问 Vue3 监控页面。

建议只读 API：

```text
GET /api/health       # Web 服务健康状态
GET /api/modules      # 六类接口连通性和收发统计
GET /api/resources    # CPU/内存/磁盘/网络占用
GET /api/ipc-status   # 大小核通信、Frame Pool、RX/TX Ring 和 Pending Bitmap 状态
GET /api/route-status # 小核路由、优先级队列、丢弃原因和出口统计
GET /api/logs         # 系统日志查询
GET /api/events       # 最近异常事件
```

典型访问流程：

```text
PC / 手机浏览器
  ↓ HTTP
Milk-V Duo 大核 put-webd
  ↓
读取 /run/put/status 快照 / /var/log/put 日志 / 系统资源
  ↓
Vue3 页面展示系统运行状态
```

## 五、anyMSG 统一数据帧设计

项目目标统一业务帧为 anyMSG。字段定义以 `docs/设计文档/统一数据帧设计.md` 为准。

anyMSG 由 40B 固定帧头和可变长度 payload 组成：

```yaml
anyMSG_protocol_structure:
  msg_length: 2Byte          # 帧总字节数，等于 40 + payload_length
  retries: 1Byte             # 重试次数
  __RESERVED__: 1Byte        # 保留字段
  __SRCHLD__: 4Byte          # 源标记，保留
  destination_cid: 4Byte     # 目的通信地址
  source_cid: 4Byte          # 源通信地址
  local_time: 4Byte          # 本地时间戳
  verify_string[16]: 16Byte  # 校验码，当前未定义真实算法
  payload_length: 2Byte      # payload 字节数
  type: 1Byte                # payload 类型
  __PADDING__: 1Byte         # 填充字段
  payload: variable          # 数据帧负载实体
```

基础规则：

- `msg_length` 必须等于 `40 + payload_length`；
- `payload_length` 不包含 40B 固定帧头；
- `destination_cid` 和 `source_cid` 使用 4B 通信地址；
- 地址首字节用于区分 CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485 等地址段；
- `type` 只描述 payload 语义，不直接规定物理出口或转发策略；
- `verify_string[16]` 当前不能作为有效业务校验依据；
- 多字节字段字节序需要在具体接口实现中保持一致。

CID 地址首字节规划：

| 地址首字节    | 定义              |
| ------------- | ----------------- |
| `0x00 ~ 0x1F` | 保留地址          |
| `0x20 ~ 0x3F` | CAN 设备地址段    |
| `0x40 ~ 0x5F` | 以太网设备地址段  |
| `0x60 ~ 0x7F` | Wi-Fi 设备地址段  |
| `0x80 ~ 0x9F` | 蓝牙设备地址段    |
| `0xA0 ~ 0xBF` | 4G 蜂窝设备地址段 |
| `0xC0 ~ 0xDF` | RS485 设备地址段  |
| `0xE0 ~ 0xFF` | 保留地址          |

目标公共头文件方向：

```text
common/include/
├── anymsg_frame.h          # anyMSG 公共定义、字段偏移、基础校验
├── shared_memory_ipc.h     # 共享内存通道、Frame Pool、Descriptor Ring
├── protocol_type.h         # type、接口 ID、CID 段、priority 枚举
└── error_code.h            # 通用错误码和丢弃原因
```

旧代码或旧文档中出现的 `unified_frame_t` 属于 v1 CAN direct 原型，只可作为历史参考。目标开发接口应迁移到完整 anyMSG + Frame Pool + Descriptor Ring。

## 六、共享内存 IPC v2 规划

共享内存 v2 不再把完整业务帧塞进固定 slot，而是使用 Frame Pool 保存完整 anyMSG，Ring 中只放描述符。

建议结构：

```text
shared_memory_region_v2
├── region_header
├── frame_pool
│   ├── frame_buffer[0]
│   ├── frame_buffer[1]
│   └── ...
├── rx_rings
│   ├── CAN_RX_RING
│   ├── ETH_RX_RING
│   ├── WIFI_RX_RING
│   ├── BT_RX_RING
│   ├── LTE_RX_RING
│   └── RS485_RX_RING
├── tx_rings
│   ├── CAN_TX_RING
│   ├── ETH_TX_RING
│   ├── WIFI_TX_RING
│   ├── BT_TX_RING
│   ├── LTE_TX_RING
│   └── RS485_TX_RING
├── rx_pending_bitmap
├── tx_pending_bitmap
└── stats / event area
```

描述符建议字段：

| 字段               | 作用                                    |
| ------------------ | --------------------------------------- |
| `frame_id`         | Frame Pool 中完整 anyMSG 的 ID          |
| `frame_offset`     | 完整 anyMSG 在 Frame Pool 中的偏移      |
| `frame_length`     | 完整 anyMSG 字节数                      |
| `source_interface` | 来源物理接口                            |
| `target_interface` | 小核路由后写入的目标接口                |
| `source_cid`       | 从 anyMSG 帧头提取的源地址              |
| `destination_cid`  | 从 anyMSG 帧头提取的目的地址            |
| `type`             | 从 anyMSG 帧头提取的 payload 类型       |
| `priority`         | 内部调度优先级，默认普通优先级          |
| `ttl`              | 内部转发 TTL，防止异常循环              |
| `epoch`            | Linux 启动纪元，用于重启恢复            |
| `crc16`            | 共享内存搬运校验                        |
| `flags`            | 校验状态、重组完成、是否需要回执等标志  |

Frame Pool 生命周期：

```text
Linux 接入层分配 frame buffer
  ↓
写入完整 anyMSG
  ↓
写 RX Ring 描述符
  ↓
小核读取并校验
  ↓
心跳 / 无路由 / TTL 过期 / 非法帧：进入回收路径
  ↓
正常路由：写入目标 TX Ring
  ↓
Linux 出口层发送完成或失败
  ↓
Linux 最终释放 frame buffer
```

必须补齐的统计：

- `frame_pool_used`
- `frame_pool_full`
- `allocated`
- `released`
- `pending_reclaim`
- `rx_ring_full`
- `tx_ring_full`
- `descriptor_crc_error`
- `drop_reason`

Ring 满时不覆盖旧描述符，必须按策略丢弃新帧或低优先级帧，并记录原因。

小核任务链路：

```text

  ↓

  ↓

  ↓

  ↓
```

## 十五、项目亮点总结

### 1. 完整 anyMSG 统一业务帧

系统以完整 anyMSG 作为统一业务帧，支持 40B 固定帧头和可变 payload，能够承载心跳、健康度、网络鉴权、服务区索引、网络隧道、Modbus、RAW_CAN、CAN_FD、UDS、J1939、CANopen 等不同 payload 语义。

### 2. 六类物理接口统一接入与出口

CAN、Ethernet、Wi-Fi、Bluetooth、4G、RS485 都是统一网关接口，任一接口都可以作为入口或出口，适合车载、工业现场、远程接入和现场调试场景。

### 3. Linux 适配层隔离协议差异

真实物理收发、协议私有头、流式分帧、分片重组和 MTU 差异都放在 Linux 适配层处理，避免共享内存层和小核路由核心被具体接口细节污染。

### 4. FreeRTOS 小核专注实时路由调度

小核只处理共享内存中的完整 anyMSG，负责头部校验、心跳消费、CID 路由、优先级调度和 TX Ring 写入，充分发挥异构多核实时控制能力。

### 5. 共享内存 v2 支持大帧和多接口队列

Frame Pool + Descriptor Ring 方案突破固定 slot 限制，支持可变长度 anyMSG、六路 RX/TX Ring、Pending Bitmap、Mailbox Doorbell 和可观测统计。

### 6. Web 可视化监控展示

系统提供 Web 监控页面，可以直观看到接口连通性、共享内存水位、路由调度状态、系统资源占用、日志和异常事件，便于现场调试、问题定位和比赛答辩演示。

### 7. 支持低功耗唤醒和黑盒式终端

使用 C51 作为低功耗管理单元，在系统空闲时进入低功耗状态，在外部数据或唤醒信号到来时恢复工作，最终作品可封装为独立黑盒网关终端。
