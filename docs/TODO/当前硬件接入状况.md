# 当前硬件接入状况

本文基于当前仓库代码审查和 Duo256M + DUO_IOB V1.11 原理图核对结果整理，目标是说明 Web 界面中六类接口状态的真实来源、各接口当前接入成熟度，以及 CAN、RS485 下一步板级接入操作。

## 1. 当前现象

早期开发板上运行 `linux_app` 与 `web` 编译产物后，Web 的“六类接口状态”中只有 `Ethernet` 显示为 `online`，其余 `CAN`、`Wi-Fi`、`Bluetooth`、`4G`、`RS485` 显示为 `disabled`，文案为：

```text
module disabled by config
```

这个现象不是 Web 前端自行推断出来的，也不是单纯的设备节点探测失败。Web 后端 `put-webd` 通过 `/api/modules` 读取 `status_dir/modules.json`，生产配置默认读取：

```text
/run/put/status/modules.json
```

该文件由 `linux_app/core/status_collector.c` 写出。也就是说，模块状态的直接来源是 `linux_app` 主程序写入的状态快照。

当前右上角总体状态仍可能显示 `ok`，是因为 `status_collector` 只把 `error`、`stale`、`offline` 计入顶层异常，`disabled` 不会把顶层状态提升为 `warn`。因此某些接口 disabled 但总状态仍是 ok，属于当前状态汇总策略，不代表所有接口都已真实在线。

当前代码已经把 `CAN`、`Wi-Fi`、`Bluetooth`、`RS485` 默认启用并接入主程序，`4G` 也已接入但默认关闭。因此上板后更可能看到：

```text
CAN: can_socket failed with error=-32
RS485: rs485_ioctl_set failed with error=-2
```

这两个错误不是 Web 前端自行判断的结果，而是 `linux_app` 写入状态快照后的真实运行状态：

- `error=-32` 对应 `UNIFIED_ERR_IPC_NOT_READY`。当前发生在 `can_adapter.c` 打开 `PF_CAN/SOCK_RAW/CAN_RAW` socket 阶段，通常表示内核 CAN/SocketCAN 栈未启用或目标 CAN 网卡没有注册出来。
- `error=-2` 对应 `UNIFIED_ERR_INVALID_ARG`。当前发生在 `rs485_adapter.c` 调用 `TIOCSRS485` 设置 RS485 模式阶段，通常表示选错 UART、UART 驱动不支持 RS485 ioctl，或方向控制 GPIO 没有通过设备树交给串口驱动。

Web 的“设备节点”页只做通配探测：CAN 会查 `/sys/class/net/can*`，RS485 只要看到 `/dev/ttyS*`、`/dev/ttyUSB*` 等串口就会显示 present。因此 RS485 present 只能说明系统有串口，不能说明配置中的串口就是板上的 RS485。

## 2. 关键代码边界

当前 `linux_app` 的核心编译单元包含 6 个物理适配器：

```text
adapters/bluetooth_adapter.c
adapters/can_adapter.c
adapters/ethernet_adapter.c
adapters/four_g_adapter.c
adapters/rs485_adapter.c
adapters/wifi_adapter.c
```

对应文件：`linux_app/CMakeLists.txt`。

`main.c` 中当前 egress adapter 绑定情况如下：

```c
egress_config.adapters[PUT_SHM_INTERFACE_CAN] = &can_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_CAN] = config.can_enabled;

egress_config.adapters[PUT_SHM_INTERFACE_ETHERNET] = &ethernet_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_ETHERNET] = config.ethernet_enabled;

egress_config.adapters[PUT_SHM_INTERFACE_WIFI] = &wifi_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_WIFI] = config.wifi_enabled;

egress_config.adapters[PUT_SHM_INTERFACE_BLUETOOTH] = &bluetooth_adapter;
egress_config.adapter_contexts[PUT_SHM_INTERFACE_BLUETOOTH] = NULL;

egress_config.enabled[PUT_SHM_INTERFACE_RS485] = config.rs485_enabled;
```

默认配置文件 `linux_app/config/device_config.ini` 当前启用了 CAN、Ethernet、Wi-Fi、Bluetooth、RS485；4G 默认关闭，避免 EC20 未插入或系统未联网时影响其它接口：

```ini
[can]
enabled = true

[ethernet]
enabled = true

[wifi]
enabled = true

[bluetooth]
enabled = true

[4g]
enabled = false

[rs485]
enabled = true
uart_device = "/dev/ttyS4"
```

`app_config_t` 当前包含 `can`、`ethernet`、`wifi`、`bluetooth`、`four_g`、`rs485` 相关配置字段。

原理图边界：

- `duo-256m-v1.01-schematic.pdf` 是 Duo256M/SG2002 模组原理图，没有直接出现 CAN 或 RS485 收发器。
- `duo_iob_v1.11.pdf` 第 4 页是实际外设底板的 `CAN&RS232&RS485` 电路：
  - CAN：`XL2515`/MCP2515 类 SPI CAN 控制器接 `SPI2_CSn`、`SPI2_RX`、`SPI2_TX`、`SPI2_SCK`，中断接 `GPIO14`，复位网络标为 `XL2515_RST`，外接 `XL1050` CAN 收发器到 `CAN_H/CAN_L`。
  - RS485：U14 RS485 收发器接 `UART4_TX`、`UART4_RX`，`RE/DE` 方向控制接 `GPIO15`，差分线为 `RS485_A_D+`、`RS485_B_D-`。

## 4. 已接入接口：Ethernet

Ethernet 是当前完整接入并默认启用的基础联调接口。

现状：

- `ethernet_adapter.c` 已加入 `linux_app_core` 编译。
- `device_config.ini` 中 `[ethernet] enabled = true`。
- `main.c` 会按配置启动 Ethernet UDP RX 和 TCP RX。
- Ethernet egress worker 已绑定 `ethernet_adapter`。
- 状态线程启动后会调用 `status_collector_mark_running()`，因此 Web 显示 `online`。

后续建议：

- 保持 Ethernet 作为基础联调通道。
- 用标准 anyMSG UDP/TCP 测试帧验证 RX 写入共享内存 RX ring。
- 用小核或 host loop 写 Ethernet TX ring，验证 egress worker、adapter send、frame release 闭环。
- 若作为外部入口，需要补齐鉴权、完整性校验和重放保护。

## 5. CAN：下一步板级接入操作

CAN 当前属于“应用层已接入，板级 SocketCAN 尚未就绪”的接口。

现状：

- `can_adapter.c` 已加入 `linux_app_core` 编译。
- `main.c` 已包含 `can_adapter_start()` 启动分支。
- CAN egress worker 已绑定 `can_adapter`。
- `device_config.ini` 中 `[can] enabled = true`，默认接口名为 `can0`。
- CAN 使用 SocketCAN classic 帧承载私有 anyMSG 分片，不是把 `ANYMSG_TYPE_RAW_CAN` 自动翻译成普通 CAN 控制帧。
- IOB 原理图显示 CAN 不是 SoC 原生控制器，而是 SPI2 外挂 `XL2515`/MCP2515 类控制器 + `XL1050` 收发器。

当前错误含义：

- Web 显示 `CAN missing`：系统没有 `/sys/class/net/can*`。
- 模块状态显示 `can_socket failed with error=-32`：应用打开 `PF_CAN/SOCK_RAW/CAN_RAW` socket 失败，优先检查内核是否启用 CAN/SocketCAN，而不是检查应用层配置。

下一步操作：

1. 确认内核配置包含 CAN/SocketCAN 和 MCP251x 驱动：

   ```text
   CONFIG_CAN=y
   CONFIG_CAN_RAW=y
   CONFIG_CAN_DEV=y
   CONFIG_CAN_MCP251X=y
   CONFIG_SPI=y
   ```

2. 在设备树中启用 SPI2，并为 `XL2515`/MCP2515 添加节点。DTS 需表达以下硬件事实：

   ```dts
   can_clock: can-clock {
       compatible = "fixed-clock";
       #clock-cells = <0>;
       clock-frequency = <15000000>;
   };

   &spi2 {
       status = "okay";
       pinctrl-names = "default";
       pinctrl-0 = <&spi2_pins>;

       can0: can@0 {
           compatible = "microchip,mcp2515";
           reg = <0>;
           clocks = <&can_clock>;
           spi-max-frequency = <10000000>;
           interrupt-parent = <&gpio>;
           interrupts = <14 IRQ_TYPE_EDGE_FALLING>;
           status = "okay";
       };
   };
   ```

   具体 `gpio` 控制器名、pinmux 名和中断写法以当前 SDK 的 SG2002/CV181x 设备树为准。若板上 `XL2515_RST` 到 `GPIO22` 的 0R 电阻未贴装，不要在 DTS 中声明 reset GPIO；若已贴装，可补 `reset-gpios = <&gpio 22 GPIO_ACTIVE_LOW>;`。

3. 重新构建并部署内核/设备树后，上板确认 `can0` 出现：

   ```bash
   dmesg | grep -Ei 'mcp|2515|can|spi'
   ip -details link show can0
   ls /sys/class/net/can0
   ```

4. 在启动 `linux_app` 前配置波特率并拉起接口：

   ```bash
   scripts/bringup_can_rs485.sh can0 500000
   ```

   或手工执行：

   ```bash
   ip link set can0 down
   ip link set can0 type can bitrate 500000 restart-ms 100
   ip link set can0 up
   ```

5. 保持或准备如下应用配置：

   ```ini
   [can]
   enabled = true
   ifname = "can0"
   bitrate = 500000
   tx_can_id = 0x321
   rx_filter_id = 0x320
   rx_filter_mask = 0x7FF
   extended_id = false
   reassembly_timeout_ms = 500
   ```

6. 使用显式配置启动：

   ```bash
   ./linux_app --config /path/to/device_config.integration.ini
   ```

7. 观察 `/run/put/status/modules.json` 中 `can.status` 是否从 `error` 变为 `online`、`stale` 或真实总线错误。
8. 做 SocketCAN 基础测试：

   ```bash
   candump can0
   cansend can0 320#A001020304050607
   ```

9. 做 PUT 应用测试：向 `rx_filter_id = 0x320` 匹配的 CAN ID 发送 anyMSG 私有分片，确认 `can.rx_frames` 和 `rx_bytes` 增长；让小核或 host loop 写 `CAN_TX_RING`，确认 egress worker 调用 `can_adapter` 并在 CAN 总线上看到分片帧。

注意：

- 如果目标是控制普通 CAN 设备，还需要定义普通 CAN payload 翻译策略。
- 当前 CAN 出口发送的是完整 anyMSG 的私有 CAN 分片，普通 CAN 设备不一定能理解。

## 6. 可以直接接入：Wi-Fi

Wi-Fi 当前属于“已具备主程序接入能力，默认启用后可通过 UDP/TCP raw anyMSG 联调”的接口。

现状：

- `wifi_adapter.c` 已加入 `linux_app_core` 编译。
- `main.c` 已包含 Wi-Fi UDP/TCP 启动分支。
- Wi-Fi egress worker 已绑定 `wifi_adapter`。
- `device_config.ini` 中 `[wifi] enabled = true`，状态取决于 UDP/TCP 监听是否启动以及是否收到业务帧。
- Wi-Fi RX 接收完整 anyMSG 帧，经基础校验后写入共享内存 RX ring。

接入步骤：

1. 确认开发板 Wi-Fi 设备已经联网或 AP 模式已启动，系统中能看到 `wlan0` 或同类接口。
2. 准备集成配置：

   ```ini
   [wifi]
   enabled = true
   udp_enabled = true
   tcp_enabled = true
   bind_addr = "0.0.0.0"
   port = 5001
   tx_peer_addr = ""
   tx_peer_port = 5001
   ```

3. 如果需要 Wi-Fi TX 回发到固定客户端，配置默认 peer：

   ```ini
   tx_peer_addr = "192.168.1.50"
   tx_peer_port = 5001
   ```

4. 如果需要按目标 Wi-Fi CID 选择不同 UDP peer，配置 `tx_peer`：

   ```ini
   tx_peer = "0x61000001,192.168.1.50,5001"
   ```

5. 使用显式配置启动 `linux_app`。
6. 观察 `/run/put/status/modules.json` 中 `wifi.status` 是否从 `disabled` 变为 `online`。
7. 用 UDP 或 TCP 发送完整 anyMSG 帧到 `5001`，源 CID 需要属于 Wi-Fi 地址段。
8. 观察 `wifi.rx_frames`、`rx_bytes`、decode error、IPC error 是否变化。
9. 做 Wi-Fi TX 测试：让小核或 host loop 写 `WIFI_TX_RING`，确认 egress worker 能通过 `wifi_adapter` 发到 peer。

注意：

- 当前 Wi-Fi 入口缺少鉴权、完整性校验和重放保护。
- 如果 Wi-Fi 面向手机或外部网络开放，不建议在未补安全策略前用于真实控制指令。
- 当前 Wi-Fi 默认 TTL 较短的问题也需要结合集成测试复核，避免调度抖动导致误丢帧。

## 7. RS485：下一步板级接入操作

RS485 当前属于“应用层已接入，串口选择和方向控制尚未对齐硬件”的接口。

现状：

- `linux_app/adapters/rs485_adapter.c` 和 `.h` 已存在。
- `rs485_adapter.c` 实现了 RX 线程、串口打开、RS485 ioctl、状态上报、TX send 等基础逻辑。
- `rs485_adapter.c` 已加入 `linux_app_core` 编译。
- `app_config_t` 已有 `rs485_enabled`、`rs485_uart_device`、`rs485_baudrate`、`rs485_flags` 字段。
- `main.c` 已调用 `rs485_adapter_start()` 并在退出路径调用 `rs485_adapter_stop()`。
- RS485 egress worker 已绑定 `rs485_adapter`。
- 当前默认 `uart_device = "/dev/ttyS4"`，对应 IOB 原理图中板上 RS485 接的 `UART4_TX`、`UART4_RX` 和 `GPIO15`。

当前错误含义：

- Web 设备节点页显示 `RS485 / Serial present`，只是因为探测到了 `/dev/ttyS*`，不代表配置中的串口就是 IOB 上的 RS485。
- 模块状态显示 `rs485_ioctl_set failed with error=-2`，说明串口打开后 `TIOCSRS485` 设置失败。常见原因是当前 UART 不是 RS485 对应 UART，或 UART 驱动没有拿到 DE/RE 方向 GPIO。

下一步操作：

1. 上板确认 `UART4` 对应的 Linux 设备节点。不要只根据串口编号猜测：

   ```bash
   dmesg | grep -Ei 'ttyS|uart|serial'
   ls -l /sys/class/tty/ttyS*/device
   cat /proc/tty/driver/serial
   ```

   如果 SDK 设备树有 aliases，也检查 `serial4` 映射。目标是找到 IOB 上 `UART4_TX/UART4_RX` 对应的 `/dev/ttySx`，多数情况下应改为 `/dev/ttyS4`，但最终以上板枚举为准。

2. 在设备树中启用 UART4，并配置 TX/RX pinmux。DTS 需表达以下硬件事实：

   ```dts
   &uart4 {
       status = "okay";
       pinctrl-names = "default";
       pinctrl-0 = <&uart4_pins>;
   };
   ```

3. 处理 `GPIO15` 的 RS485 方向控制。U14 的 `RE`/`DE` 共用 `GPIO15`，典型逻辑是发送时 GPIO15 为高，发送结束后为低进入接收。

   优先方案是把 GPIO15 交给 UART 驱动：

   ```dts
   &uart4 {
       status = "okay";
       linux,rs485-enabled-at-boot-time;
       rs485-rts-gpios = <&gpio 15 GPIO_ACTIVE_HIGH>;
       rs485-rts-delay = <0 0>;
   };
   ```

   具体属性是否可用取决于当前串口驱动。本次接入不加入用户态 GPIO15 fallback；如果驱动不支持 `rs485-rts-gpios` 或 `TIOCSRS485`，`linux_app` 会保持 RS485 error/offline，完整接入需先补驱动或 DTS。`rs485_flags = 0` 仅可用于原始 UART 电气排查，不作为半双工 RS485 验收路径。

4. 修正应用配置，先把 RS485 指向 UART4 对应节点。若 UART 驱动支持 RS485 ioctl，建议方向极性从 `0x3` 开始验证：

   ```ini
   [rs485]
   enabled = true
   uart_device = "/dev/ttyS4"
   baudrate = 115200
   rs485_flags = 0x3
   ```

   `0x3` 表示 `SER_RS485_ENABLED | SER_RS485_RTS_ON_SEND`，与 U14 的 DE 高电平发送模型对齐。若示波器或对端测试显示方向反了，优先调整 DTS GPIO 极性；确认为驱动 RTS 语义反向时再改 `rs485_flags`。

5. 启动 `linux_app` 后观察状态：

   ```bash
   cat /run/put/status/modules.json
   ```

   预期 `rs485.status` 不再是 `error`，`last_error` 不再是 `rs485_ioctl_set failed with error=-2`。

6. 做串口基础验证：

   ```bash
   stty -F /dev/ttyS4 115200 raw -echo
   cat /dev/ttyS4
   printf '\x01\x03\x00\x00\x00\x01' > /dev/ttyS4
   ```

   若使用外部 USB-RS485 对端，确认 A/B 没接反，必要时交换 `RS485_A_D+` 与 `RS485_B_D-`。

7. 做 PUT 应用验证：RS485 对端发送裸数据，确认 `rs485.rx_frames` 和 `rs485.rx_bytes` 增长；通过 TX ring 写目标 CID 为 RS485 段的 anyMSG，确认物理串口只发送 payload 裸数据。

注意：

- 当前 RS485 RX 会把裸串口数据封装成 `RS485_ANYMSG_TYPE_RAW`，默认 destination CID 是保留段，这可能导致路由侧拒绝或无法转发，需要根据业务补目标 CID 策略。
- 当前 TX 逻辑会剥离 anyMSG 头，只发送 payload 裸数据，适合透传，但需要明确 Modbus/私有协议边界。
- 当前 Web 资源探测会把所有 `/dev/ttyS*` 都算作 RS485/Serial present，后续应改成按 `device_config.ini` 中的 `rs485_uart_device` 精确展示。

## 8. 已接入但需板级验证：Bluetooth

Bluetooth 当前已接入 `linux_app` 的主程序和 egress 路径，默认配置启用 RFCOMM channel 1。它仍不适合作为无安全保护的真实控制入口；配对、会话鉴权、CID 授权和重放保护还需要单独设计。

现状：

- `bluetooth_adapter.c` 已加入 `linux_app_core` 编译。
- `app_config_t` 已包含 `bluetooth_enabled`、`bluetooth_channel` 配置字段。
- `main.c` 会按配置调用 `bluetooth_server_start()`，退出时调用 `bluetooth_server_stop()`。
- Bluetooth egress worker 已绑定 `bluetooth_adapter`。
- RX 线程按 anyMSG `msg_length` 切帧，校验 source CID 属于 Bluetooth 地址段后写入 `PUT_SHM_INTERFACE_BLUETOOTH` RX ring。
- TX 在已有 RFCOMM 客户端连接时发送完整 anyMSG；没有客户端连接时会记录 `bt_send_no_client`。
- 当前还缺少专门的 `bluetooth_adapter_test` 和板级 RFCOMM 闭环验证。

接入步骤：

1. 确认内核和系统镜像包含 Bluetooth/RFCOMM 支持，应用运行权限允许创建 `AF_BLUETOOTH` / `BTPROTO_RFCOMM` socket。
2. 确认蓝牙控制器已上电并完成基本 bringup，例如 `hciconfig`、`bluetoothctl` 或系统侧蓝牙服务能看到本机设备。
3. 保持或准备如下应用配置：

   ```ini
   [bluetooth]
   enabled = true
   channel = 1
   ```

4. 启动 `linux_app` 后观察 `/run/put/status/modules.json` 中 Bluetooth 状态；如果启动失败，优先检查内核协议族、权限和控制器状态。
5. 使用 RFCOMM 客户端连接 channel 1，发送完整 anyMSG 帧，确认 `bluetooth.rx_frames` 和 `rx_bytes` 增长。
6. 让小核或 host loop 写 `BLUETOOTH_TX_RING`，确认 egress worker 能通过已连接客户端发送，并在发送失败时正确记录错误。
7. 补单元测试和 host loop 测试，至少覆盖合法 Bluetooth anyMSG 写入 RX ring、非法长度/非法 CID 被拒绝、未连接客户端 TX 失败路径。

注意：

- Bluetooth 面向手机或近距离外部设备，安全边界比内部总线复杂。
- 进入真实控制场景前，应定义配对、会话鉴权、重放保护、CID 授权策略。

## 9. 可以直接接入：4G（EC20 USB 网卡模式）

4G 当前已按 **EC20 USB 网卡/IP 网络接口模式**接入 `linux_app`。`linux_app` 不负责 SIM/APN、AT、PPP、QMI/MBIM 或拨号流程；系统侧需要先把 EC20 拉起为可用 IP 网卡。

现状：

- `linux_app/adapters/four_g_adapter.c` 和 `.h` 已存在并加入 CMake。
- `app_config_t` 已新增 `four_g_*` 配置字段，配置文件使用 `[4g]`，兼容 `[four_g]`。
- `main.c` 已绑定 `PUT_SHM_INTERFACE_4G` egress adapter，并按配置启动 4G UDP/TCP RX server。
- 4G RX 会校验 source CID 属于 `0xA0~0xBF`，然后写入 `PUT_SHM_INTERFACE_4G` RX ring。
- 4G TX 会校验 destination CID 属于 `0xA0~0xBF`，然后通过 UDP 发往默认 peer 或 CID-specific peer。
- 默认配置仍保持 `enabled = false`，避免未插 EC20 或未联网时影响其它接口启动。

上板前先确认 EC20 已成为可用网卡，默认接口名按 `usb0`：

```bash
ip link
ip addr show usb0
ping -I usb0 8.8.8.8
```

启用配置示例：

```ini
[4g]
enabled = true
ifname = "usb0"
bind_to_device = true
udp_enabled = true
tcp_enabled = true
bind_addr = "0.0.0.0"
port = 5002
tx_peer_addr = ""
tx_peer_port = 5002
# tx_peer = "0xA1000001,192.168.10.100,5002"
```

注意：

- `bind_to_device = true` 会让 4G UDP/TCP socket 绑定到 `ifname`，部署时通常需要 root 或相应 capability。
- 如果 EC20 在系统中显示为 `wwan0`、`ppp0` 或其它接口名，需要同步修改 `ifname`。
- 4G 属于远程入口，真实控制场景仍建议补鉴权、完整性校验、重放保护和限流。

## 10. 推荐接入顺序

建议按风险和代码成熟度排序：

1. Ethernet：保持为基准通道，先完善测试和状态显示。
2. CAN：补内核/DTS 让 SPI2 外挂 CAN 控制器注册为 `can0`，再验证 SocketCAN RX/TX。
3. Wi-Fi：打开配置并验证 UDP/TCP anyMSG，适合作为第二个新增 online 接口。
4. RS485：应用层已接入，后续做 UART4/GPIO15 DTS 和板级串口/总线联调。
5. Bluetooth：应用层已接入，后续做 RFCOMM 板级闭环和安全策略。
6. 4G：EC20 USB 网卡模式已实现；后续如要由 `linux_app` 管理拨号，再单独扩展 AT/PPP/QMI/MBIM 控制面。

## 12. 验收标准

接入任一接口后，应满足以下最小验收标准：

1. CMake 编译通过，目标程序包含对应 adapter。
2. `main.c` 有明确启动和停止生命周期。
3. `app_config_t` 有配置字段，配置文件可显式启用/禁用。
4. `status_collector` 中能区分 disabled、online、offline、error。
5. Web `/api/modules` 能显示接口状态和 RX/TX 计数。
6. RX 方向能把合法 anyMSG 写入对应 RX ring。
7. TX 方向能从对应 TX ring 出队，调用 adapter send，并释放 frame。
8. 接口 disabled 时，TX frame 不应被静默误判为成功。
9. 非法帧、接口离线、发送失败必须有明确错误计数和事件。
10. 至少有一条 host 测试或板级测试覆盖该接口的 RX/TX 基础闭环。

## 13. 当前一句话结论

当前主程序已接入 Ethernet、CAN、Wi-Fi、Bluetooth、RS485，以及按 EC20 USB 网卡模式实现的 4G；其中 4G 默认关闭，启用前需确认系统已把 EC20 拉起为 `usb0`、`wwan0`、`ppp0` 等可用 IP 网卡。CAN 和 RS485 的主要阻塞点在板级内核/DTS，Bluetooth 的主要风险在系统蓝牙 bringup 和安全策略。
