# 当前硬件接入状况

本文基于当前仓库代码审查结果整理，目标是说明 Web 界面中六类接口状态的真实来源、各接口当前接入成熟度，以及后续把接口接入 `linux_app` 主程序的实现步骤。

## 1. 当前现象

开发板上已经运行 `linux_app` 与 `web` 编译产物后，Web 的“六类接口状态”中只有 `Ethernet` 显示为 `online`，其余 `CAN`、`Wi-Fi`、`Bluetooth`、`4G`、`RS485` 显示为 `disabled`，文案为：

```text
module disabled by config
```

这个现象不是 Web 前端自行推断出来的，也不是单纯的设备节点探测失败。Web 后端 `put-webd` 通过 `/api/modules` 读取 `status_dir/modules.json`，生产配置默认读取：

```text
/run/put/status/modules.json
```

该文件由 `linux_app/core/status_collector.c` 写出。也就是说，模块状态的直接来源是 `linux_app` 主程序写入的状态快照。

当前右上角总体状态仍可能显示 `ok`，是因为 `status_collector` 只把 `error`、`stale`、`offline` 计入顶层异常，`disabled` 不会把顶层状态提升为 `warn`。因此 5 个接口 disabled 但总状态仍是 ok，属于当前状态汇总策略，不代表 6 类接口全部可用。

## 2. 关键代码边界

当前 `linux_app` 的核心编译单元只包含 3 个物理适配器：

```text
adapters/can_adapter.c
adapters/ethernet_adapter.c
adapters/wifi_adapter.c
```

对应文件：`linux_app/CMakeLists.txt`。

`main.c` 中当前 egress adapter 绑定情况如下：

```c
egress_config.adapters[PUT_SHM_INTERFACE_CAN] = &can_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_CAN] = config.can_enabled;

egress_config.adapters[PUT_SHM_INTERFACE_ETHERNET] = &ethernet_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_ETHERNET] = config.ethernet_enabled;

egress_config.adapters[PUT_SHM_INTERFACE_WIFI] = &wifi_adapter;
egress_config.enabled[PUT_SHM_INTERFACE_WIFI] = config.wifi_enabled;

egress_config.enabled[PUT_SHM_INTERFACE_BLUETOOTH] = false;
egress_config.enabled[PUT_SHM_INTERFACE_4G] = false;
egress_config.enabled[PUT_SHM_INTERFACE_RS485] = false;
```

默认配置文件 `linux_app/config/device_config.ini` 当前只启用了 Ethernet：

```ini
[can]
enabled = false

[ethernet]
enabled = true

[wifi]
enabled = false

[bluetooth]
enabled = false
```

`app_config_t` 当前也只包含 `can`、`ethernet`、`wifi`、`bluetooth` 相关配置字段，没有 `4g` 和 `rs485` 配置字段。

## 3. 接入状态总表

| 接口 | Web 当前表现 | 当前代码状态 | 是否可以直接接入主程序 | 说明 |
| --- | --- | --- | --- | --- |
| Ethernet | online | 已编译、已配置、已启动 UDP/TCP RX/TX | 已接入 | 当前唯一默认启用并运行的接口。 |
| CAN | disabled | 已编译、已有主程序启动分支、默认配置关闭 | 可以直接接入 | 打开配置并准备 SocketCAN 后即可进入主程序路径。 |
| Wi-Fi | disabled | 已编译、已有主程序启动分支、默认配置关闭 | 可以直接接入 | 与 Ethernet 类似，使用 UDP/TCP raw anyMSG 承载。 |
| RS485 | disabled | 有适配器源码雏形，但未编译、无主配置、无主程序启动分支 | 可以较小改动接入 | 不是“只改配置即可”，需要补 CMake、配置解析和生命周期。 |
| Bluetooth | disabled | 有源码雏形，但未编译，且存在接口不匹配和占位逻辑 | 不能直接接入 | 需要先重构适配器并接入统一状态与 IPC。 |
| 4G | disabled | 没有独立 4G adapter，没有配置字段，主程序硬编码关闭 | 不能直接接入 | 需要新增 adapter 与配置模型。 |

## 4. 已接入接口：Ethernet

Ethernet 是当前唯一完整接入并默认启用的接口。

现状：

- `ethernet_adapter.c` 已加入 `linux_app_core` 编译。
- `device_config.ini` 中 `[ethernet] enabled = true`。
- `main.c` 会按配置启动 Ethernet UDP RX 和 TCP RX。
- Ethernet egress worker 已绑定 `ethernet_adapter`。
- 状态线程启动后会调用 `status_collector_mark_running()`，因此 Web 显示 `online`。

后续建议：

- 保持 Ethernet 作为基础联调通道。
- 用标准 anyMSG UDP/TCP 测试帧验证 RX 写入共享内存 RX ring。
- 用小核或 host loop 写 Ethernet TX ring，验证 egress worker、adapter send、frame release 闭环。
- 若作为外部入口，需要补齐鉴权、完整性校验和重放保护。

## 5. 可以直接接入：CAN

CAN 当前属于“已具备主程序接入能力，但默认关闭”的接口。

现状：

- `can_adapter.c` 已加入 `linux_app_core` 编译。
- `main.c` 已包含 `can_adapter_start()` 启动分支。
- CAN egress worker 已绑定 `can_adapter`。
- `device_config.ini` 中 `[can] enabled = false`，所以 Web 显示 disabled。
- CAN 使用 SocketCAN classic 帧承载私有 anyMSG 分片，不是把 `ANYMSG_TYPE_RAW_CAN` 自动翻译成普通 CAN 控制帧。

接入步骤：

1. 确认开发板内核支持 CAN/SocketCAN，并能看到目标接口，例如 `can0`。
2. 在启动 `linux_app` 前由系统脚本或手工命令配置 CAN 波特率并拉起接口，例如：

   ```bash
   ip link set can0 type can bitrate 500000
   ip link set can0 up
   ```

3. 修改或准备集成配置文件：

   ```ini
   [can]
   enabled = true
   ifname = "can0"
   bitrate = 500000
   tx_can_id = 0x321
   rx_filter_id = 0x320
   rx_filter_mask = 0x7FF
   extended_id = false
   reassembly_timeout_ms = 500
   ```

4. 使用显式配置启动：

   ```bash
   ./linux_app --config /path/to/device_config.integration.ini
   ```

5. 观察 `/run/put/status/modules.json` 中 `can.status` 是否从 `disabled` 变为 `online`、`stale` 或 `error`。
6. 如显示 `error` 或 `offline`，优先检查 SocketCAN 接口是否存在、是否 up、滤波 ID 是否匹配、板级 CAN 收发器是否接好。
7. 做 CAN RX 测试：向 `rx_filter_id` 匹配的 CAN ID 发送 anyMSG 私有分片，确认 `can.rx_frames` 和 `rx_bytes` 增长。
8. 做 CAN TX 测试：让小核或 host loop 写 `CAN_TX_RING`，确认 egress worker 调用 `can_adapter` 并在 CAN 总线上看到分片帧。

注意：

- 如果目标是控制普通 CAN 设备，还需要定义普通 CAN payload 翻译策略。
- 当前 CAN 出口发送的是完整 anyMSG 的私有 CAN 分片，普通 CAN 设备不一定能理解。

## 6. 可以直接接入：Wi-Fi

Wi-Fi 当前属于“已具备主程序接入能力，但默认关闭”的接口。

现状：

- `wifi_adapter.c` 已加入 `linux_app_core` 编译。
- `main.c` 已包含 Wi-Fi UDP/TCP 启动分支。
- Wi-Fi egress worker 已绑定 `wifi_adapter`。
- `device_config.ini` 中 `[wifi] enabled = false`，所以 Web 显示 disabled。
- Wi-Fi RX 接收完整 anyMSG 帧，经基础校验后写入共享内存 RX ring。

接入步骤：

1. 确认开发板 Wi-Fi 设备已经联网或 AP 模式已启动，系统中能看到 `wlan0` 或同类接口。
2. 准备集成配置：

   ```ini
   [wifi]
   enabled = true
   udp_enabled = true
   tcp_enabled = true
   bind_addr = "0.0.0.0"
   port = 5001
   tx_peer_addr = ""
   tx_peer_port = 5001
   ```

3. 如果需要 Wi-Fi TX 回发到固定客户端，配置默认 peer：

   ```ini
   tx_peer_addr = "192.168.1.50"
   tx_peer_port = 5001
   ```

4. 如果需要按目标 Wi-Fi CID 选择不同 UDP peer，配置 `tx_peer`：

   ```ini
   tx_peer = "0x61000001,192.168.1.50,5001"
   ```

5. 使用显式配置启动 `linux_app`。
6. 观察 `/run/put/status/modules.json` 中 `wifi.status` 是否从 `disabled` 变为 `online`。
7. 用 UDP 或 TCP 发送完整 anyMSG 帧到 `5001`，源 CID 需要属于 Wi-Fi 地址段。
8. 观察 `wifi.rx_frames`、`rx_bytes`、decode error、IPC error 是否变化。
9. 做 Wi-Fi TX 测试：让小核或 host loop 写 `WIFI_TX_RING`，确认 egress worker 能通过 `wifi_adapter` 发到 peer。

注意：

- 当前 Wi-Fi 入口缺少鉴权、完整性校验和重放保护。
- 如果 Wi-Fi 面向手机或外部网络开放，不建议在未补安全策略前用于真实控制指令。
- 当前 Wi-Fi 默认 TTL 较短的问题也需要结合集成测试复核，避免调度抖动导致误丢帧。

## 7. 可以较小改动接入：RS485

RS485 当前不是“直接改配置即可接入”，但它已有较完整的适配器源码雏形，单文件编译检查可通过，属于可以较小工程改动接入的接口。

现状：

- `linux_app/adapters/rs485_adapter.c` 和 `.h` 已存在。
- `rs485_adapter.c` 实现了 RX 线程、串口打开、RS485 ioctl、状态上报、TX send 等基础逻辑。
- 当前 CMake 没有编译 `rs485_adapter.c`。
- 当前 `app_config_t` 没有 `rs485_enabled`、`rs485_uart_device`、`rs485_baudrate` 等字段。
- 当前 `main.c` 没有调用 `rs485_adapter_start()`。
- 当前 egress 中 `PUT_SHM_INTERFACE_RS485` 被硬编码为 disabled。

接入步骤：

1. 将 `adapters/rs485_adapter.c` 加入 `linux_app/CMakeLists.txt` 的 `linux_app_core` 源文件列表。
2. 在 `app_config_t` 中新增 RS485 配置字段，建议最小字段如下：

   ```c
   bool rs485_enabled;
   char rs485_uart_device[64];
   uint32_t rs485_baudrate;
   uint32_t rs485_flags;
   ```

3. 在 `app_config_set_defaults()` 中设置默认值：

   ```text
   enabled = false
   uart_device = "/dev/ttyS1"
   baudrate = 115200
   rs485_flags = SER_RS485_ENABLED | SER_RS485_RTS_AFTER_SEND
   ```

4. 在 `app_config_load_file()` 的解析逻辑中新增 `[rs485]` section，例如：

   ```ini
   [rs485]
   enabled = true
   uart_device = "/dev/ttyS1"
   baudrate = 115200
   ```

5. 在 `app_config_validate()` 中校验：

   - `uart_device` 非空；
   - `baudrate` 是驱动支持值；
   - enabled 时配置合法。

6. 在 `main.c` 中包含 `rs485_adapter.h`。
7. 在 `configure_status_modules()` 中把 RS485 的 enabled 来源改成 `config->rs485_enabled`，不要继续硬编码 `false`。
8. 在 egress 配置中绑定 RS485 adapter：

   ```c
   egress_config.adapters[PUT_SHM_INTERFACE_RS485] = &rs485_adapter;
   egress_config.adapter_contexts[PUT_SHM_INTERFACE_RS485] = NULL;
   egress_config.enabled[PUT_SHM_INTERFACE_RS485] = config.rs485_enabled;
   ```

9. 在共享内存初始化完成后，按配置创建并启动 `rs485_adapter_config_t`：

   ```c
   rs485_adapter_config_set_defaults(&rs485_config);
   rs485_config.enabled = config.rs485_enabled;
   snprintf(rs485_config.uart_device, sizeof(rs485_config.uart_device), "%s", config.rs485_uart_device);
   rs485_config.baudrate = config.rs485_baudrate;
   rs485_config.ipc = &ipc;
   rs485_config.collector = &collector;
   rs485_config.linux_epoch = linux_epoch;
   rs485_adapter_start(&rs485_config);
   ```

10. 在退出路径中调用 `rs485_adapter_stop()`。
11. 上板验证 `/dev/ttyS1` 或实际 RS485 串口设备是否存在。
12. 观察 `/run/put/status/modules.json` 中 `rs485.status` 是否变化。
13. 用串口工具或 RS485 对端发送数据，验证 RX 计数和 IPC commit。
14. 通过 TX ring 写目标 CID 为 RS485 段的 anyMSG，验证物理串口发送。

注意：

- 当前 RS485 RX 会把裸串口数据封装成 `RS485_ANYMSG_TYPE_RAW`，默认 destination CID 是保留段，这可能导致路由侧拒绝或无法转发，需要根据业务补目标 CID 策略。
- 当前 TX 逻辑会剥离 anyMSG 头，只发送 payload 裸数据，适合透传，但需要明确 Modbus/私有协议边界。

## 8. 暂不能直接接入：Bluetooth

Bluetooth 当前不能直接接入主程序。它不是单纯未启用，而是代码仍处于占位/接口未对齐状态。

现状：

- `bluetooth_adapter.c` 当前未加入 CMake 编译。
- `main.c` 中如果 `bluetooth_enabled = true`，会直接报 `bluetooth adapter unavailable: adapter binding is not implemented` 并退出。
- `bluetooth_adapter.c` 调用了当前 `status_collector.h` 中不存在的 `status_collector_register_adapter()` 和 `status_collector_unregister_adapter()`。
- `bluetooth_get_mtu()` 返回类型与 `physical_interface_adapter_t.get_mtu` 不匹配。
- `bluetooth_reassemble()` 函数签名与统一适配器接口不匹配。
- `bluetooth_decode_rx()` 只做长度检查，没有完整 anyMSG 静态字段校验，也没有填充 `adapter_rx_result_t`。
- RX 线程收到完整帧后只更新本地计数，没有写入共享内存 RX ring。
- TX `encapsulate` 当前返回成功但没有填充输出 packet，直接接入 egress 有产生假成功或空发送的风险。

接入步骤：

1. 先不要通过简单打开 `bluetooth.enabled=true` 接入主程序。
2. 重构 `bluetooth_adapter.c`，使其完全匹配 `physical_interface_adapter_t`：

   - `get_mtu` 返回 `size_t`；
   - `reassemble` 使用 `adapter_fragment_t` 和 `anymsg_buffer_t` 签名；
   - `status` 与当前统一 status 接口匹配；
   - 删除或替换不存在的 register/unregister API。

3. 复用 Ethernet/Wi-Fi 的 anyMSG 校验逻辑：

   - 校验 `msg_length`；
   - 校验 `payload_length`；
   - 校验保留字段；
   - 校验 source CID 属于 Bluetooth 地址段；
   - 填充 `adapter_rx_result_t`。

4. 新增 `bluetooth_adapter_submit_to_ipc()`，将完整 anyMSG 写入 `BLUETOOTH_RX_RING`。
5. RX 线程收到合法帧后调用 submit，而不是只更新本地计数。
6. 补齐 TX `encapsulate` 或 `fragment_tx`，确保 egress worker 能得到有效 packet。
7. 将 `bluetooth_adapter.c` 加入 CMake。
8. 在 `app_config_t` 中保留并完善 Bluetooth 配置，如 channel、listen backlog、安全策略等。
9. 在 `main.c` 中移除“启用即退出”的保护逻辑，改为真实启动 `bluetooth_server_start()` 或统一 adapter 生命周期。
10. 在 egress 配置中绑定 `bluetooth_adapter` 并按配置启用。
11. 加入单元测试和 host loop 测试，至少覆盖：

    - 合法 Bluetooth anyMSG 写入 RX ring；
    - 非法长度/非法 CID 被拒绝；
    - TX ring 到 Bluetooth send 的释放闭环；
    - 未连接客户端时状态显示 offline/error，而不是假 online。

注意：

- Bluetooth 面向手机或近距离外部设备，安全边界比内部总线复杂。
- 接入前应定义配对、会话鉴权、重放保护、CID 授权策略。

## 9. 暂不能直接接入：4G

4G 当前没有可接入主程序的 adapter。

现状：

- 没有 `4g_adapter.c` 或同等 4G 适配器实现。
- `app_config_t` 没有 4G 配置字段。
- `main.c` 中 4G status 和 egress 都被硬编码为 disabled。
- Web 的 `/api/resources` 可以探测 4G/Cellular 相关设备节点，但这只是资源探测，不等价于 anyMSG 接入。

接入步骤：

1. 明确 4G 模块工作模式：

   - PPP 拨号；
   - QMI/MBIM；
   - ECM/RNDIS/NCM 网卡；
   - AT 串口控制 + 数据通道。

2. 如果 4G 模块最终表现为 IP 网络接口，优先复用 Ethernet/Wi-Fi 的 UDP/TCP raw anyMSG 模型，新建 `4g_adapter` 只是为了隔离配置、状态和 peer 策略。
3. 新增 `linux_app/adapters/four_g_adapter.c` 和 `.h`，或采用项目统一命名 `cellular_adapter.c`。
4. 新增配置字段：

   ```ini
   [four_g]
   enabled = true
   udp_enabled = true
   tcp_enabled = true
   bind_addr = "0.0.0.0"
   port = 5002
   tx_peer_addr = ""
   tx_peer_port = 5002
   ifname = "wwan0"
   ```

5. 在 `app_config_t` 中加入 4G 配置并解析校验。
6. 在 `main.c` 中配置 status、egress adapter、RX server 生命周期和退出清理。
7. 实现 4G RX 到 `PUT_SHM_INTERFACE_4G` RX ring。
8. 实现 4G TX ring 到 UDP/TCP peer 或模块数据通道的发送。
9. Web/status 中区分以下状态：

   - 模块硬件不存在；
   - 模块存在但未拨号；
   - 网络接口存在但无 IP；
   - 业务监听已启动；
   - anyMSG RX/TX 活跃。

10. 增加 4G 限流和鉴权策略，避免远程入口耗尽共享内存。

## 10. 推荐接入顺序

建议按风险和代码成熟度排序：

1. Ethernet：保持为基准通道，先完善测试和状态显示。
2. CAN：打开配置并验证 SocketCAN RX/TX，适合作为第一个新增 online 接口。
3. Wi-Fi：打开配置并验证 UDP/TCP anyMSG，适合作为第二个新增 online 接口。
4. RS485：补 CMake、配置、主程序生命周期后接入。
5. Bluetooth：先重构 adapter 和安全边界，再接入。
6. 4G：先定义模块工作模式，再实现 adapter。

## 11. 最小集成配置建议

为避免默认生产配置和集成测试配置混用，建议新增：

```text
linux_app/config/device_config.integration.ini
```

示例：

```ini
[status]
enabled = true
dir = "/run/put/status"

[can]
enabled = true
ifname = "can0"
bitrate = 500000
tx_can_id = 0x321
rx_filter_id = 0x320
rx_filter_mask = 0x7FF
extended_id = false
reassembly_timeout_ms = 500

[ethernet]
enabled = true
udp_enabled = true
tcp_enabled = true
bind_addr = "0.0.0.0"
port = 5000
tx_peer_addr = ""
tx_peer_port = 5000

[wifi]
enabled = true
udp_enabled = true
tcp_enabled = true

```

RS485 和 4G 在补齐配置模型前不建议写入该集成配置，避免出现“配置看似存在但程序完全忽略”的误导。

## 12. 验收标准

接入任一接口后，应满足以下最小验收标准：

1. CMake 编译通过，目标程序包含对应 adapter。
2. `main.c` 有明确启动和停止生命周期。
3. `app_config_t` 有配置字段，配置文件可显式启用/禁用。
4. `status_collector` 中能区分 disabled、online、offline、error。
5. Web `/api/modules` 能显示接口状态和 RX/TX 计数。
6. RX 方向能把合法 anyMSG 写入对应 RX ring。
7. TX 方向能从对应 TX ring 出队，调用 adapter send，并释放 frame。
8. 接口 disabled 时，TX frame 不应被静默误判为成功。
9. 非法帧、接口离线、发送失败必须有明确错误计数和事件。
10. 至少有一条 host 测试或板级测试覆盖该接口的 RX/TX 基础闭环。

## 13. 当前一句话结论

当前主程序实际完整接入并默认启用的是 Ethernet；CAN 和 Wi-Fi 已具备直接接入条件，只需要启用配置并准备硬件/网络；RS485 有适配器雏形，需补 CMake、配置和主程序生命周期；Bluetooth 和 4G 当前不能直接接入，分别需要重构适配器和新增 adapter。
