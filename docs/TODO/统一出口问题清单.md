# 统一出口问题清单

来源：`c8fc5f9 实现用于IPC处理的出口管理器和工作线程` 代码审查  
日期：2026-05-29  
排序规则：按风险优先级从高到低排列。

---

## P0 高风险

### 1. Ethernet / Wi-Fi 出口 CID 与 IPv4 目标地址语义冲突

问题：

- `egress_worker` 要求 `destination_cid[0]` 落在目标接口 CID 段，例如 Ethernet 为 `0x40~0x5F`、Wi-Fi 为 `0x60~0x7F`。
- `ethernet_send()` / `wifi_send()` 又把 `destination_cid[0..3]` 直接作为 IPv4 地址发送。
- 这会导致合法 IPv4 地址如 `127.0.0.1` 无法通过统一出口 worker 的 CID 校验；测试目前绕过了 worker，只直接测 adapter。

解决方案：

- 保持统一出口原则：物理出口由 TX Ring / `target_interface` 决定，CID 只做一致性检查，不直接等同网络地址。
- 新增 Ethernet / Wi-Fi TX peer 映射策略：按 `destination_cid` 查表得到 IPv4/端口；第一版可用固定默认 peer 或配置表，不从 CID raw bytes 直接 memcpy 成 IPv4。
- `ethernet_tx_context_t` / `wifi_tx_context_t` 增加 peer 配置或 resolver 回调；未找到 peer 时 `send()` 返回失败并记录 `send_no_peer`。
- 更新测试：新增经过 `egress_worker_drain_once()` 的 Ethernet/Wi-Fi TX 成功用例，覆盖 CID 段合法、peer 映射存在、UDP 实际收到完整 anyMSG。
- 保留 adapter 直测，但测试数据必须使用合法 CID 段，IPv4 由 TX context 提供。

验收标准：

- `destination_cid[0] = 0x40~0x5F` 的 Ethernet 帧可经 worker 发送到配置的 IPv4 peer。
- `destination_cid[0] = 0x60~0x7F` 的 Wi-Fi 帧可经 worker 发送到配置的 IPv4 peer。
- 保留 CID、目标接口错配、peer 缺失都会释放 frame 并记录明确错误。
- 不再有测试通过改写 `destination_cid` 为 `127.0.0.1` 来绕过统一出口校验。

## P1 中高风险

### 2. CAN 出口 `write()` 可能阻塞，导致 worker 和停止流程卡住

问题：

- `can_send()` 对 SocketCAN fd 直接调用阻塞式 `write()`。
- 当前只设置了 `SO_RCVTIMEO`，没有 TX 超时或非阻塞发送策略。
- 当 CAN TX 队列拥塞、接口异常或驱动长时间不返回时，CAN worker 会卡住，`egress_manager_stop()` join worker 时也可能卡住。

解决方案：

- 在 CAN socket 打开后设置发送超时：`SO_SNDTIMEO = CAN_ADAPTER_SOCKET_TIMEOUT_US`，或将 socket 设为 `O_NONBLOCK`。
- `can_send()` 明确处理 `EAGAIN`、`EWOULDBLOCK`、`ENOBUFS`、`ENETDOWN`、`ENODEV`：
  - 临时拥塞计为 `can_send_busy`；
  - 接口离线计为 `can_send_offline`；
  - 短写计为 `can_send_short`。
- 任一 CAN 分片发送失败时，统一出口按整条 anyMSG 失败处理，释放 Frame Pool block，不在出口层无限重试。
- 若使用 `can_tx_context_t.socket_fd`，启动 CAN RX 服务成功后应显式同步可发送 fd，或继续使用 `g_can_state.socket_fd` 但加锁保护 TX 状态更新。

验收标准：

- CAN fd 无效、离线、拥塞时 `can_send()` 有界返回失败。
- `egress_manager_stop()` 在 CAN 发送异常场景下可以正常退出。
- CAN 分片任一失败时只记录一次完整 anyMSG 发送失败，并释放 frame。
- 新增单测或可注入 mock fd/发送函数覆盖 busy、offline、short write。

## P1 中高风险

### 3. Bluetooth 启用后没有绑定 adapter，TX 帧会被释放丢弃

问题：

- `main.c` 允许 `config.bluetooth_enabled` 使 Bluetooth egress worker 处于 enabled。
- 但当前没有注册 `bluetooth_adapter` 和 adapter context。
- 结果是 Bluetooth TX Ring 出队后进入 `adapter_missing` 分支，frame 被释放，业务上表现为静默丢弃。

解决方案：

- 在蓝牙物理适配器实现接入前，启动配置中强制 Bluetooth egress disabled。
- 若 `bluetooth_enabled=true` 但未编译/未绑定 `bluetooth_adapter`，启动阶段返回配置错误或记录 `bluetooth_adapter_unavailable`，不要运行后静默 drop。
- 后续接入真实蓝牙时，再在 `egress_config.adapters[PUT_SHM_INTERFACE_BLUETOOTH]` 绑定 `bluetooth_adapter`，并补齐 TX context。
- 状态文案从“egress placeholder is observable”改为“Bluetooth egress unavailable until adapter binding is implemented”。

验收标准：

- 当前版本设置 `bluetooth.enabled=true` 时不会静默丢弃 Bluetooth TX frame。
- Web/status 能明确看到 Bluetooth egress 未绑定或不支持。
- 接入真实 `bluetooth_adapter` 后，Bluetooth TX 走 worker、send、release 的完整闭环。
