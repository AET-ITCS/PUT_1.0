# 软件集成问题清单

来源：当前代码审查，围绕“在不考虑硬件限制的情况下，手机是否可以通过 Wi-Fi 或蓝牙发送特定 anyMSG 帧，向网关连接的 CAN 设备下发控制指令”进行软件链路评估。  
日期：2026-06-01  
排序规则：按端到端可达性和安全风险优先级排列。

---

## 1. 当前结论

### 1.1 Wi-Fi 到 CAN 的软件链路

在 host 代码和测试层面，Wi-Fi 入口到 CAN 出口的核心软件链路已经具备雏形：

```textfloccus
手机 / 外部客户端
  -> Wi-Fi UDP/TCP 原始 anyMSG
  -> linux_app Wi-Fi RX
  -> Linux shared memory RX ring
  -> RTOS router
  -> CAN TX ring
  -> Linux egress worker
  -> SocketCAN classic CAN 私有分片发送
```

当前 Wi-Fi 接入代码会接收完整 anyMSG 帧，校验基础长度、保留字段和源 CID 段后，将帧写入 `WIFI_RX_RING`。如果 `destination_cid[0]` 落在 CAN 地址段 `0x20 ~ 0x3F`，目标接口会被标记为 CAN。RTOS 路由表默认也会把 CAN CID 段路由到 `PUT_SHM_INTERFACE_CAN`。

但是，这条链路目前不能直接认定为“手机可以安全控制普通 CAN 设备”。主要原因有三点：

1. 当前真实固件入口还没有启动 RTOS 任务调度闭环。
2. Wi-Fi 外部入口缺少鉴权、完整性校验和重放保护。
3. CAN 出口发送的是完整 anyMSG 的私有 CAN 分片，不是普通 CAN 控制报文语义转换。

### 1.2 蓝牙到 CAN 的软件链路

蓝牙路径目前不可用：

1. `linux_app` 在 `bluetooth_enabled = true` 时会直接报错退出。
2. `linux_app/CMakeLists.txt` 没有把 `bluetooth_adapter.c` 编入 `linux_app_core`。
3. 蓝牙接收线程只做长度读取和统计计数，没有把帧提交到共享内存 RX ring。
4. 蓝牙 `decode_rx`、`encapsulate`、`fragment_tx` 仍是占位实现，未对齐 `physical_interface_adapter_t` 的完整收发约定。

## 2. P0 高风险问题

### 2.1 外部 Wi-Fi 入口缺少鉴权和重放保护

现状：

- `linux_app/adapters/wifi_adapter.c` 中 `wifi_adapter_decode_datagram()` 只校验：
  - 帧长度在 `ANYMSG_HEADER_SIZE` 到 `PUT_SHM_FRAME_POOL_BLOCK_SIZE` 范围内；
  - `msg_length == 40 + payload_length`；
  - anyMSG 保留字段为 0；
  - `source_cid[0]` 属于 Wi-Fi CID 段。
- `wifi_adapter_submit_to_ipc()` 随后直接把帧写入共享内存 RX ring。
- `rtos_firmware/router/rtos_router_adapter.c` 当前把所有通过 descriptor 适配的输入固定标记为 `RTOS_ROUTE_TRUST_AUTH_OK`。
- `verify_string[16]` 在当前 anyMSG 文档中尚未定义真实算法，不能作为有效鉴权依据。

风险：

- 任意能访问网关 Wi-Fi UDP/TCP 端口的客户端，只要构造基础合法的 anyMSG，就可能把目标 CID 指向 CAN 段，从而进入 CAN 路由链路。
- 伪造 `source_cid`、`destination_cid`、`type` 和 payload 的成本很低。
- 控制帧、服务帧和 CAN 相关类型没有可信来源限制。
- 重放旧控制帧没有阻断机制。

解决方案：

- 在 Linux 接入层引入入口会话鉴权，至少支持以下一种或组合：
  - 基于预共享密钥的 HMAC；
  - 短期 token；
  - TLS/DTLS 或等价加密会话；
  - 已配对设备白名单和会话绑定。
- 为 Wi-Fi/TCP 会话维护 `session_id`、`sequence`、`nonce` 或 timestamp 窗口，阻断重放。
- 明确 `verify_string[16]` 的用途：
  - 如果保留为业务 MAC，则定义算法、覆盖范围、密钥轮换和错误统计；
  - 如果不用作鉴权，则文档和代码都要明确不得依赖该字段。
- 扩展共享内存 descriptor 或控制区的可信状态表达，使 Linux 可以向 RTOS 明确传递：
  - `AUTH_OK`；
  - `AUTH_FAILED`；
  - `INTEGRITY_FAILED`；
  - `REPLAY_DROPPED`。
- RTOS 适配层不得再无条件设置 `RTOS_ROUTE_TRUST_AUTH_OK`。
- 对 priority 0/1 或控制类 type 增加更严格的入口策略，只允许认证通过且来源被授权的会话进入路由。

验收标准：

- 未携带合法认证材料的 Wi-Fi anyMSG 不会进入 RTOS Router Scheduler。
- 重放同一控制帧会被丢弃，并产生可观测统计。
- Web/status 日志能区分鉴权失败、完整性失败和重放丢弃。
- 单元测试覆盖合法帧、伪造 token、错误 MAC、重放 sequence、过期 timestamp。

### 2.2 RTOS 任务调度闭环尚未接入真实固件入口

现状：

- `rtos_firmware/tasks/rtos_tasks.c` 已经实现 host 单步调度能力：
  - drain RX ring；
  - descriptor 转 route input；
  - RTOS router 入队；
  - scheduler 写目标 TX ring；
  - reclaim sink 回收丢弃帧。
- 但是 `rtos_firmware/main.c` 当前只是 smoke 入口，注释明确写着真实 RTOS scheduler 后续再接入。
- `rtos_firmware/src/rtos_entry.c` 目前只初始化 BSP、CAN 占位层和 watchdog，占位后直接返回。

风险：

- host 测试通过只能说明组件级链路可用，不能说明真实固件运行时会自动处理 Linux 写入的 RX descriptor。
- Linux Wi-Fi RX 即使成功写入 `WIFI_RX_RING`，如果小核真实任务没有启动，帧会停留在共享内存中，无法进入 CAN TX ring。
- `tx_pending_bitmap` 和 `rx_pending_bitmap` 的门铃/周期扫描策略无法在真实目标上被验证。

解决方案：

- 在真实 RTOS 入口中创建并启动以下任务或等价 event loop：
  - IPC Event Task：响应 Linux->RTOS doorbell，drain RX ring；
  - Router Scheduler Task：从本地优先级队列调度并写 TX ring；
  - Reclaim Task：处理心跳消费、无路由、非法帧、TTL 过期等回收；
  - Monitor/Statistics Task：刷新状态、错误和水位统计；
  - Heartbeat Task：维护 Linux 心跳和端到网关心跳表。
- 将 `rtos_tasks_context_init()` 接到固件初始化流程，确保共享内存 attach、Linux epoch、路由表和 monitor 状态同步。
- 明确 mailbox doorbell 与周期兜底 drain 的时序。
- 增加目标侧 smoke 测试：Linux 写 RX descriptor 后，RTOS 能在限定时间内写目标 TX descriptor。

验收标准：

- 在无硬件 CAN 的 host loop 中，Wi-Fi RX descriptor 能被 RTOS 自动搬运到 CAN TX ring。
- 在真实固件入口中，启动后能观察到 RX pending 被消费、TX pending 被设置。
- scheduler 不依赖手动调用 host test 函数。
- Recovery 场景下不会遗留 Frame Pool block。

### 2.3 CAN 出口当前发送 anyMSG-over-CAN 私有分片，不是普通 CAN 控制语义

现状：

- `linux_app/adapters/can_adapter.c` 的 `can_fragment_tx()` 会把完整 anyMSG 按私有经典 CAN 分片协议发送：
  - 先发 SOF 帧，包含 session、总长度、CRC、数据帧数量；
  - 再发 DATA 帧，每帧承载完整 anyMSG 的连续字节片段。
- CAN ID 使用配置中的固定 `tx_can_id`，默认配置为 `0x321`。
- 出口层不解析 payload，也不把 `ANYMSG_TYPE_RAW_CAN` payload 翻译成普通 CAN ID + DLC + data。

风险：

- 如果网关连接的是普通 CAN 设备，设备大概率无法理解 anyMSG 私有分片协议。
- 用户以为发送 `type = RAW_CAN` 就会下发普通 CAN 控制帧，但当前实现实际下发的是“封装后的完整 anyMSG 字节流”。
- 控制指令语义边界不清：`type` 表示 payload 类型，但不决定物理出口，也不定义普通 CAN 帧映射。

解决方案：

需要先明确产品目标，然后二选一或同时支持：

方案 A：继续使用 anyMSG-over-CAN。

- 明确 CAN 设备必须实现同一套 anyMSG 私有分片重组协议。
- 在 CAN 模块设计文档中写清楚 SOF/DATA 帧格式、CRC、session、超时和重传策略。
- 手机端只负责发完整 anyMSG，CAN 设备侧负责重组和解释 payload。

方案 B：支持普通 CAN 控制帧下发。

- 定义 `ANYMSG_TYPE_RAW_CAN` payload 格式，例如：

```text
can_id: 4 bytes
flags: 1 byte
dlc: 1 byte
data: 0..8 bytes
```

- 在 CAN 出口 worker 或 CAN adapter 中增加 RAW_CAN payload 解析。
- 对普通 CAN、CAN FD、ISO-TP 分别定义 payload 编码和发送策略。
- 对 CAN ID、DLC、扩展帧标志、RTR、错误帧等字段做严格白名单和边界校验。
- 为不同 CAN 设备或功能定义授权策略，避免认证客户端任意写总线。

验收标准：

- 文档明确说明 CAN 目标设备需要理解 anyMSG 分片，还是网关会翻译成普通 CAN 帧。
- RAW_CAN 下发测试能在 vcan 上观察到预期 CAN ID 和 data。
- 非法 CAN ID、非法 DLC、payload 长度不匹配会被拒绝。
- 发送失败会释放 Frame Pool，并记录明确错误阶段。

### 2.4 蓝牙接入和出口未集成

现状：

- `linux_app/main.c` 中 `bluetooth_enabled` 为 true 时直接返回失败。
- `linux_app/CMakeLists.txt` 未编译 `bluetooth_adapter.c`。
- 蓝牙接收线程读取完整帧后，只更新 `rx_count`、`rx_bytes`、`last_seen_ms`。
- 蓝牙代码注释明确标记“此处分配共享内存并写 RX Ring”为占位。
- 蓝牙 `decode_rx` 只检查长度，没有完整 anyMSG 头部校验，也没有填充 `adapter_rx_result_t`。
- 蓝牙出口 `encapsulate` 返回成功但不填充 `out_packet`，如果直接接入 egress worker 会产生发送路径风险。

风险：

- 当前无法通过蓝牙向 CAN 下发控制指令。
- 如果只打开编译和启动开关，而不补齐适配器实现，可能出现空 packet、未初始化字段或假成功统计。
- 蓝牙安全边界更复杂，需要同时处理配对、会话、权限和重放问题。

解决方案：

- 将蓝牙适配器按 Wi-Fi/Ethernet 的入口模型重构：
  - `bluetooth_decode_rx()` 使用统一 anyMSG 校验；
  - 填充 `adapter_rx_result_t`；
  - 增加 `bluetooth_adapter_submit_to_ipc()`；
  - 接收线程调用 submit 写 `BLUETOOTH_RX_RING`。
- 修正蓝牙 `physical_interface_adapter_t` 回调签名和实现：
  - `reassemble` 应匹配 `adapter_fragment_t` 输入；
  - `encapsulate` 必须填充 `out_packet->data` 和 `out_packet->len`；
  - `fragment_tx` 不能假成功。
- 将 `bluetooth_adapter.c` 编入 CMake，并在 `main.c` 中真正启动/停止蓝牙服务。
- 蓝牙启用前，先定义安全策略：
  - 配对设备白名单；
  - 会话级 token/MAC；
  - sequence 或 nonce 防重放；
  - 可下发目的 CID 和 CAN 功能白名单。

验收标准：

- `bluetooth_enabled = true` 不再导致 `linux_app` 启动失败。
- 蓝牙合法 anyMSG 能进入 `BLUETOOTH_RX_RING`。
- 目标 CID 为 CAN 段时，RTOS 能路由到 `CAN_TX_RING`。
- 未认证蓝牙客户端不能写入 RX ring。
- 单元测试覆盖蓝牙 decode、stream 切帧、IPC submit、出口 packet 填充。

## 3. P1 中高风险问题

### 3.1 默认配置与集成配置边界需要清晰

现状：

- `linux_app/config/device_config.ini` 中：
  - `[can] enabled = true`
  - `[wifi] enabled = true`
  - `[rs485] enabled = true`
  - `[rs485] uart_device = "/dev/ttyS4"`
  - `[bluetooth] enabled = false`
- 已新增 `linux_app/config/device_config.integration.ini`，用于 CAN/RS485/Wi-Fi 上板集成。
- CAN egress worker、CAN RX、Wi-Fi UDP/TCP、RS485 RX/TX 均按配置启用；CAN 仍依赖外部 `can0` 和 bitrate bring-up。

风险：

- 测试人员可能把板级内核/DTS 未完成误判成应用层未接入。
- 默认配置和集成配置如果继续分化，可能导致 Web 状态与测试步骤不一致。
- 即使应用配置启用 CAN/RS485，缺少 `can0`、UART4 或 `TIOCSRS485` 驱动支持时仍会显示真实 error。

解决方案：

- 使用 `linux_app/config/device_config.integration.ini` 做上板集成配置：
  - Wi-Fi enabled；
  - CAN enabled，接口名 `can0`；
  - RS485 enabled，串口默认 `/dev/ttyS4`，`rs485_flags = 0x3`；
  - 明确监听地址和端口。
- 使用 `scripts/bringup_can_rs485.sh can0 500000` 在启动 `linux_app` 前配置 SocketCAN。
- 状态快照中突出显示当前接口 enabled/running/listening/socket_open。

验收标准：

- 使用集成配置启动后，Wi-Fi UDP/TCP 监听成功，CAN/RS485 egress enabled。
- 默认生产配置和集成测试配置边界清晰。
- Web 或 status 文件能直观看出接口是板级缺失、驱动 ioctl 失败还是链路成功。

### 3.2 `type` 与物理出口、业务语义之间仍容易混淆

现状：

- 当前设计原则是 `destination_cid` 决定目标物理接口，`type` 只描述 payload 语义。
- RTOS router 会接受多类 type，包括心跳、网络认证、服务索引、隧道映射、Modbus、CAN、UDS、J1939、CANopen。
- 出口层不会因为 `type = RAW_CAN` 自动改变 CAN 发送方式。

风险：

- 上层客户端可能错误地认为只要设置 `type = RAW_CAN`，就一定会生成普通 CAN 控制帧。
- 如果目的 CID 指向 CAN，但 type 是非 CAN 业务类型，当前路由仍可能进入 CAN 出口，只要类型被策略认为合法。

解决方案：

- 增加“接口允许 type 白名单”策略：
  - CAN 出口只允许 RAW_CAN、CAN_FD、CAN_ISOTP、UDS、J1939、CANOPEN 或明确允许的管理帧；
  - Wi-Fi/Ethernet/Bluetooth 出口按业务场景配置允许 type；
  - 心跳类帧按 gateway/endpoint 方向特殊处理。
- 在 RTOS router 或 egress worker 中增加目标接口与 type 的一致性校验。
- 文档中明确 `type` 不决定路由，但目标接口可以拒绝不支持的 type。

验收标准：

- 目的 CID 为 CAN 但 type 为无关服务索引时，不会发到 CAN 总线。
- 拒绝原因可观测，例如 `unsupported_type_for_interface`。
- 单元测试覆盖各接口 type 白名单。

### 3.3 TTL 当前以 8 毫秒作为 Wi-Fi 默认值，集成环境下可能误丢

现状：

- `WIFI_ADAPTER_DEFAULT_TTL` 为 `8u`。
- RTOS router 会在 submit 和 schedule 阶段检查 TTL。
- 当前 host 测试中时间源多为可控或默认，真实运行后 8ms 对跨 Linux、共享内存、RTOS 调度、出口发送可能偏紧。

风险：

- 手机通过 Wi-Fi 发来的控制帧在正常调度抖动下也可能 TTL 过期。
- 问题表现为偶发丢帧，容易被误判为 Wi-Fi 或 CAN 发送失败。

解决方案：

- 将 Wi-Fi 默认 TTL 改为配置项。
- 为控制帧、普通数据帧、低优先级数据帧分别定义默认 TTL。
- 在状态统计中记录 TTL 过期计数和最大排队延迟。
- 集成压测后再收敛默认 TTL。

验收标准：

- Wi-Fi TTL 可通过配置调整。
- TTL 过期原因在 Web/status 中可见。
- 压测报告给出建议 TTL 范围。

## 4. P2 中风险问题

### 4.1 缺少手机端 anyMSG 构造与集成测试工具

现状：

- 仓库中已有 adapter 和 host loop 测试，但没有面向手机/外部客户端的 anyMSG 构造工具或示例。
- 没有统一的 Wi-Fi UDP/TCP 发帧示例。

解决方案：

- 增加一个测试工具，支持：
  - 构造 anyMSG header；
  - 设置 source CID、destination CID、type、payload；
  - 自动填充 little-endian length 字段；
  - UDP 或 TCP 发送；
  - 可选 token/MAC；
  - 可选 sequence/nonce。
- 同时增加 vcan 集成测试脚本：
  - 启动 linux_app；
  - 发送 Wi-Fi anyMSG；
  - 驱动 RTOS host loop 或真实 RTOS mock；
  - 观察 CAN TX 输出。

验收标准：

- 开发者可以用一条命令发送目标 CID 为 CAN 的测试帧。
- 测试工具能生成合法和非法样例，覆盖鉴权失败、CID 错误、长度错误。

### 4.2 状态和日志需要体现端到端链路位置

现状：

- 已有 status collector 和 IPC stats，但端到端问题定位仍需要跨 Wi-Fi、RTOS、egress、CAN 多处查找。

解决方案：

- 为每个 frame 增加可观测链路阶段统计：
  - Wi-Fi RX accepted；
  - RX ring enqueue；
  - RTOS drain；
  - router enqueue；
  - TX ring enqueue；
  - egress dequeue；
  - CAN fragment generated；
  - CAN send success/fail；
  - frame released。
- 状态文件中增加按接口的 drop reason 汇总。
- 对安全拒绝、TTL 过期、接口禁用、CAN offline 分别记录明确 stage。

验收标准：

- 单帧失败能定位到明确阶段。
- Web/status 能区分“没进 Wi-Fi RX”“RTOS 未调度”“CAN egress disabled”“SocketCAN offline”。

## 5. 建议实施顺序

1. 先补齐 Wi-Fi 外部入口鉴权、完整性校验和重放保护，禁止未认证控制帧进入 RTOS。
2. 接入真实 RTOS 任务调度闭环，让 RX ring 到 TX ring 不再依赖 host 单步测试。
3. 明确 CAN 下发语义：选择 anyMSG-over-CAN 或普通 CAN payload 翻译，优先补文档和测试。
4. 增加 vcan/host loop 端到端集成测试，覆盖 Wi-Fi -> CAN。
5. 再实现蓝牙接入，避免把占位适配器提前接入生产路径。
6. 最后扩展状态可观测性和手机端测试工具。
