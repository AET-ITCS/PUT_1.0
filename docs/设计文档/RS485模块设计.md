# RS485 模块设计说明书 (v2 anyMSG 架构)

## 1. 模块定位与背景

在多协议 anyMSG 网关项目中，RS485 是非常核心且常见的工业通信物理接口。由于该网关采用双核架构，大核 Linux 侧（基于 Milk-V Duo 256M 平台）负责处理包括 RS485 在内的所有物理层数据的真实收发，并将数据解包为标准的 `anyMSG` 帧；小核 FreeRTOS 仅负责路由与队列调度，不直接干预 RS485 硬件层收发或方向控制。

### 1.1 设计目标
1. **彻底融入 anyMSG v2 架构**：RS485 作为六路物理接口之一，与共享内存 IPC（RX Ring / TX Ring + Frame Pool）进行解耦交互，传输业务数据全部由 `anyMSG` 统一定义。
2. **基于 Linux 驱动的自动流控**：RS485 是半双工总线，采用大核 Linux UART `tty` 驱动原生的 `TIOCSRS485` 机制进行自动发送/接收使能（DE/RE）控制，无需用户态手动控制 GPIO。
3. **支持工业 Modbus 与自定义协议流**：除了作为 `anyMSG` 帧的透明传输通道外，模块向下应具备基本的流式切帧与组包能力（基于超时或固定包头设计），以解决串口常见的“粘包”、“断包”问题。
4. **状态与监控一致性**：与其他物理网络模块一样，将自身状态与统计数据通过指针安全地注册到全局收集器 `status_collector_t`。

## 2. 整体架构与业务流

RS485 模块在大核 Linux 进程中作为一个**独立子线程（或独立的 Event Loop，如 epoll）**存在。主要业务流程如下：

### 2.1 接收数据流 (RX Path)
```text
外部 RS485 设备或传感器网络
      ↓ (半双工串行总线，波特率通常为 9600/115200 等)
大核 Linux tty 驱动 (硬件 / 驱动层接管 DE/RE 引脚变低使能接收)
      ↓
大核 RS485 接收线程 (read 系统调用或 epoll 事件触发)
      ↓ (依据 Modbus RTU 的 3.5 字符超时或 anyMSG 帧头长度做切帧)
适配器 decode_rx 校验并提取完整的载荷数据
      ↓ (封装出 anyMSG 完整帧，向 Frame Pool 申请内存块)
大核写共享内存 RS485 RX Ring 描述符
      ↓ (设置 rx_pending_bitmap 并发送 Mailbox Doorbell 唤醒小核)
小核 FreeRTOS 路由调度 (依据目标 CID 将数据转发到其它 TX Ring)
```

### 2.2 发送数据流 (TX Path)
```text
小核路由决策完毕，将描述符写入 RS485 TX Ring
      ↓ (设置 tx_pending_bitmap 并发送 Mailbox Doorbell 唤醒 Linux)
Linux 出口执行单元检测到 RS485 TX Ring 有数据
      ↓ (从 Frame Pool 读取出完整的 anyMSG)
RS485 适配器 encapsulate (可能剥离 anyMSG 包头，仅取出 payload 加上 CRC16)
      ↓ (通过 write() 系统调用向 tty 节点写入)
大核 Linux tty 驱动 (底层驱动自动拉高 DE 发送使能引脚发送数据，发完自动拉低)
      ↓
外部 RS485 设备
```

## 3. 半双工方向控制与驱动对接

为了达到高实时性，防止 Linux 用户态线程调度抖动导致的响应过慢，**RS485 的收发使能（DE/RE）必须由 Linux 驱动层接管**。

在应用层代码初始化串口时，需要通过 `ioctl` 开启串口的 RS485 模式：

```c
#include <linux/serial.h>
#include <sys/ioctl.h>

// RS485 配置伪代码
struct serial_rs485 rs485conf;

/* 尝试获取当前 RS485 配置 */
if (ioctl(fd, TIOCGRS485, &rs485conf) < 0) {
    // 错误处理
}

/* 开启 RS485 模式，并配置引脚电平逻辑 */
rs485conf.flags |= SER_RS485_ENABLED;

// 取决于实际开发板原理图配置：
// 如果发送时 DE 为高电平，则清除 SER_RS485_RTS_ON_SEND
rs485conf.flags &= ~SER_RS485_RTS_ON_SEND; 
// 接收时拉低
rs485conf.flags |= SER_RS485_RTS_AFTER_SEND; 

// 配置延迟(如有需要)
rs485conf.delay_rts_before_send = 0;
rs485conf.delay_rts_after_send = 0;

if (ioctl(fd, TIOCSRS485, &rs485conf) < 0) {
    // 错误处理，配置失败
}
```

通过以上配置，用户空间通过 `write(fd, buf, len)` 写入数据时，内核会自动拉高方向引脚，写入完成后立即释放总线供其他从机应答。

## 4. 数据帧协议与寻址 (CID)

根据《统一数据帧设计.md》的要求，RS485 数据被封装为 `anyMSG` 时遵循以下规则：

* **RS485 接口的 CID 段**：`0xC0 ~ 0xDF`
* **设备寻址**：外部 RS485 从站或网络对应的虚拟地址都应落在此区间，例如某个具体的 RS485 传感器可映射到 CID `0xC0000001`。
* **业务 Payload 类型 (`type`)**：
  * `0x47`：Modbus RTU (网关需负责剥离与添加 CRC)。
  * `0x1F` (或其他保留段)：原始 RS485 字节流透传。

## 5. 适配器接口实现

在 `linux_app/adapters/rs485_adapter.c` 中，需实现 `physical_interface_adapter_t` 表以统一接入 `protocol_manager`。

```c
extern physical_interface_adapter_t rs485_adapter;

physical_interface_adapter_t rs485_adapter = {
    .name = "RS485",
    .interface_id = 0x06,                         // RS485 全局标识 ID
    .get_mtu = rs485_get_mtu,                     // 获取 RS485 的物理层 MTU（如 Modbus 常用 256）
    .decode_rx = rs485_decode_rx,                 // 将串行输入解码为 anyMSG 或合法载荷
    .reassemble = rs485_reassemble,               // (视情况) 重组超长帧
    .encapsulate = rs485_encapsulate,             // 将 anyMSG 封装打包（添加 RTU CRC 等）
    .fragment_tx = rs485_fragment_tx,             // 大于物理 MTU 时分片
    .send = rs485_send,                           // 通过系统调用 write(fd) 发送
    .status = rs485_get_status                    // 输出运行状态
};
```

### 5.1 动态流式切帧与错误处理
RS485 作为 UART 设备是无边界流，必须具备**鲁棒的切帧能力**，常见切帧方案为：
1. **基于长度切帧**（如果承载标准的 `anyMSG` 或有定长帧头的协议）。
2. **基于时间间隔切帧**（如通过内核驱动 `VTIME` 和 `VMIN` 配置，或使用 `select/poll` 超时机制来模拟 Modbus RTU 的 3.5 字符帧间隔）。

> [!WARNING]
> **异常处理与恢复：**
> 如果发生了总线噪声干扰导致的 CRC 错误或 `anyMSG` 长度解析越界，必须清空当前串口缓冲区中的所有脏数据，并上报 `parse_error_count`。防止将错误的乱序数据带入下一个正确的帧包络中。

## 6. 统一状态收集 (Status Collection)

为兼容整个系统的监控架构，RS485 模块必须包含 `rs485_status_t` 并在初始化时注册到 `status_collector_t` 收集器。

主要需要统计与上报的字段：
* `rx_count` / `tx_count` / `rx_bytes` / `tx_bytes`
* `error_count`：串口底层读写错误。
* `crc_error_count`：Modbus 或 anyMSG 帧尾校验失败次数。
* `parse_error_count`：帧长度越界或组包超时断帧。
* `last_seen_ms`：最后接收到合法数据的时间（用于判断 RS485 链路是否健康活跃）。

使用独立的互斥或无锁传递手段，确保 Web 服务（`put-webd`）以异步非阻塞形式拿到上述健康与诊断信息。
