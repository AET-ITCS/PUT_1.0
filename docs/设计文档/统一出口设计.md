# anyMSG 统一出口设计

版本号：0.1.0
修改时间：2026-05-28
文档定位：描述 Linux 大核统一出口层设计，从 FreeRTOS 小核写入 TX Ring 开始，到物理接口真实发送和 Frame Pool 最终释放为止

---

## 1. 文档边界

本文定义 anyMSG 目标 v2 架构中的统一出口层，包括 TX Ring 消费、出口调度、物理适配器发送、错误处理、Frame Pool 释放、reclaim 回收闭环和状态统计。

本文不定义：

1. anyMSG 帧结构、字段语义、CID 地址段和 `type` 类型，见《统一数据帧设计》。
2. Linux 接入层解包、分片重组和写 RX Ring 流程，见《整体架构设计》和各物理模块设计。
3. FreeRTOS 小核路由、优先级调度、心跳消费和 reclaim 生成流程，见《freeRTOS核设计》。
4. 共享内存 v2 ABI 结构体布局，见《共享内存 IPC 架构设计方案》和 `common/include/shared_memory_ipc.h`。
5. Web 监控 API 和页面设计，见《web模块设计》。

本设计不新增公共 ABI，不修改 anyMSG 帧格式，不修改共享内存 v2 descriptor 结构。

---

## 2. 出口层定位

统一出口层运行在大核 Linux 侧。它只处理小核已经完成路由并写入目标 TX Ring 的完整 anyMSG descriptor。

出口层所在链路如下：

```text
FreeRTOS 小核路由调度
  ↓ 写目标物理接口 TX Ring descriptor
TX Pending Bitmap + Mailbox Doorbell
  ↓
Linux 统一出口调度器
  ↓ 唤醒对应物理接口出口 worker
对应接口 TX Ring
  ↓ linux_shm_dequeue_tx_descriptor()
Frame Pool 中完整 anyMSG
  ↓
physical_interface_adapter_t
  ↓ encapsulate / fragment_tx / send
CAN / Ethernet / Wi-Fi / Bluetooth / 4G / RS485
  ↓
发送完成或失败后 linux_shm_frame_release()
```

核心原则：

```text
小核决定目标 TX Ring；
Linux 出口层执行真实发送；
出口层不重新路由；
出口层不修改完整 anyMSG；
Linux 是 Frame Pool 的最终释放者。
```

---

## 3. 设计目标

1. 六类物理接口使用统一出口模型，避免每个模块各自直接读共享内存。
2. 出口层只消费对应 TX Ring，保证小核路由结果不被 Linux 二次改写。
3. 每个物理接口出口相互隔离，一个接口阻塞、离线或发送失败不能影响其他接口。
4. 所有从 TX Ring 出队的 Frame Pool block 必须最终释放，不能产生泄漏。
5. 小核消费或丢弃但未转发的帧必须通过 reclaim ring 被 Linux 回收。
6. 出口层必须记录可观测统计，供 Web 只读快照和日志展示。
7. 当前版本不实现 anyMSG 端到端重试，`retries` 字段不参与出口重发策略。

---

## 4. 职责边界

| 模块 | 负责 | 不负责 |
| ---- | ---- | ------ |
| FreeRTOS 小核 | 根据 `destination_cid` 路由，写目标接口 TX Ring，设置 `tx_pending_bitmap`，Doorbell 通知 Linux | 真实物理发送、接口重连、Frame Pool 最终释放 |
| Linux 统一出口调度器 | 读取 TX pending 状态，唤醒接口 worker，周期 drain reclaim ring，汇总出口统计 | 修改小核路由结果、解析业务 payload |
| Linux 出口 worker | 消费本接口 TX Ring，读取完整 anyMSG，调用适配器封包/分片/发送，释放 Frame Pool block | 消费其他接口 TX Ring、长期缓存业务帧 |
| 物理接口适配器 | 执行接口私有封包、分片、真实发送和接口状态查询 | 改写 anyMSG 头部、决定跨接口路由 |
| 共享内存 IPC | 校验 descriptor CRC、接口一致性、Frame Pool 状态和 pending bit 竞态 | 解释业务 payload、执行物理发送 |
| 状态收集器 | 记录 tx、错误、IPC、reclaim 和接口状态统计 | 控制物理接口、直接读写共享内存 |

出口层必须遵守以下边界：

1. `type` 只描述 payload 语义，不直接规定物理出口。
2. 物理出口只由小核写入的 `target_interface` 和 TX Ring 归属决定。
3. 出口层不得改写 `msg_length`、`payload_length`、CID、`type`、`verify_string[16]` 或 payload。
4. 出口层发现 descriptor 或 anyMSG 异常时，只记录错误、释放可释放资源，不把失败帧退回小核。
5. 出口层不向 RX Ring 回灌发送失败帧。

## 5. 使用的公共接口

统一出口层继续使用现有公共接口，不扩展 ABI。

### 5.1 共享内存 IPC 接口

| 接口 | 用途 |
| ---- | ---- |
| `linux_shm_dequeue_tx_descriptor()` | 从目标接口 TX Ring 出队 descriptor，并返回 Frame Pool 中完整 anyMSG 指针 |
| `linux_shm_frame_release()` | 发送完成或失败后释放已经进入 `TX_READY` 状态的 Frame Pool block |
| `linux_shm_dequeue_reclaim_descriptor()` | 从 reclaim ring 回收小核消费或丢弃的 RX_QUEUED frame |
| `linux_shm_ipc_get_stats()` | 获取 Frame Pool、Ring、Pending Bitmap、Mailbox 和 reclaim 统计 |

`linux_shm_dequeue_tx_descriptor()` 已负责：

1. 校验 TX Ring 格式；
2. 校验 descriptor CRC；
3. 校验 `target_interface == ring.interface_id`；
4. 校验 Frame Pool block 已分配且处于可由小核回写 TX descriptor 的状态；
5. 对成功出队的 frame 标记为 `TX_READY`；
6. 按 pending bitmap 清除规则处理竞态。

出口层仍应在业务发送前执行 anyMSG 基础校验，作为物理发送前的最后防线。

### 5.2 物理适配器接口

统一出口层通过 `physical_interface_adapter_t` 访问真实物理发送能力：

```c
typedef struct {
    const char *name;
    uint8_t interface_id;

    size_t (*get_mtu)(void *ctx);
    int (*encapsulate)(void *ctx,
                       const anymsg_buffer_t *msg,
                       adapter_tx_packet_t *out_packet);
    int (*fragment_tx)(void *ctx,
                       const anymsg_buffer_t *msg,
                       adapter_tx_packet_list_t *out_packets);
    int (*send)(void *ctx, const adapter_tx_packet_t *packet);
    int (*status)(void *ctx, void *out_status);
} physical_interface_adapter_t;
```

出口层只依赖发送相关回调。`decode_rx` 和 `reassemble` 属于接入方向，不在出口主流程中调用。

### 5.3 状态收集接口

| 接口 | 用途 |
| ---- | ---- |
| `status_collector_record_tx_ok()` | 成功发送完整 anyMSG 后累计 tx frames / tx bytes |
| `status_collector_record_error()` | 记录封包失败、分片失败、发送失败、接口离线、IPC 错误等 |
| `status_collector_update_ipc_stats()` | 周期写入 IPC、Ring、Pending Bitmap、reclaim 等状态快照 |

当前 `put_shm_reclaim_reason_t` 主要服务 reclaim 路径。TX 发送失败原因不通过扩展 reclaim reason 表达，而是通过状态统计和日志记录。

## 6. 接口映射

统一出口层固定支持六类物理接口。

| interface ID | 物理接口 | CID 首字节段 | 默认出口 worker |
| ------------ | -------- | ------------ | --------------- |
| `0` | CAN | `0x20 ~ 0x3F` | `can_tx_worker` |
| `1` | Ethernet | `0x40 ~ 0x5F` | `ethernet_tx_worker` |
| `2` | Wi-Fi | `0x60 ~ 0x7F` | `wifi_tx_worker` |
| `3` | Bluetooth | `0x80 ~ 0x9F` | `bluetooth_tx_worker` |
| `4` | 4G | `0xA0 ~ 0xBF` | `four_g_tx_worker` |
| `5` | RS485 | `0xC0 ~ 0xDF` | `rs485_tx_worker` |

注意：

1. 出口 worker 与 TX Ring 一一对应。
2. 出口 worker 不根据 CID 重新选择接口。
3. CID 段只用于一致性检查和诊断日志。
4. 保留 CID 段原则上不应被小核路由到真实物理 TX Ring；若出现，出口层记录 `invalid_cid` 或 `reserved_cid` 类错误并释放 frame。

## 7. 线程与调度模型

推荐实现采用：

```text
统一出口调度器
  ├── CAN TX worker
  ├── Ethernet TX worker
  ├── Wi-Fi TX worker
  ├── Bluetooth TX worker
  ├── 4G TX worker
  └── RS485 TX worker
```

统一出口调度器负责：

1. 接收 RTOS 到 Linux 的 Mailbox Doorbell；
2. 周期读取 `tx_pending_bitmap`，兜底处理 Doorbell 丢失；
3. 根据 pending bit 唤醒对应出口 worker；
4. 周期 drain reclaim ring；
5. 周期刷新 IPC 统计到 `status_collector_t`。

出口 worker 负责：

1. 只读取自己的 TX Ring；
2. 循环出队 descriptor，直到 TX Ring 为空、达到本轮预算或收到停止信号；
3. 调用本接口适配器完成封包、分片和发送；
4. 发送成功或失败后释放 Frame Pool block；
5. 记录本接口出口统计。

执行模型可以是独立 pthread，也可以是统一 event loop 中的 per-interface task。无论采用哪种模型，必须满足：

1. 任一接口 `send()` 阻塞或失败不能阻塞其他接口；
2. 任一接口离线不能导致 TX Ring 其他接口积压；
3. worker 每轮处理预算建议默认 `16` 个 descriptor，避免单接口长时间独占调度；
4. Doorbell 丢失时，统一出口调度器必须通过周期 drain 兜底，默认周期建议 `100ms`；
5. `send()` 不得无限阻塞，真实超时值由各适配器配置。

## 8. 统一出口主流程

### 8.1 Doorbell 触发流程

```text
RTOS 写目标 TX Ring
  ↓
RTOS 设置 tx_pending_bitmap 对应 bit
  ↓
TX Ring empty -> non-empty 时 Mailbox Doorbell
  ↓
Linux Mailbox handler 唤醒统一出口调度器
  ↓
统一出口调度器读取 tx_pending_bitmap
  ↓
唤醒所有 pending 接口 worker
```

### 8.2 周期兜底流程

```text
每 100ms 周期 tick
  ↓
统一出口调度器读取 tx_pending_bitmap
  ↓
发现 pending 接口则唤醒对应 worker
  ↓
drain reclaim ring
  ↓
刷新 IPC 状态快照
```

### 8.3 单接口 worker 流程

```text
worker 被唤醒
  ↓
linux_shm_dequeue_tx_descriptor(interface_id)
  ├── QUEUE_EMPTY：本轮结束
  ├── CRC / FORMAT / INVALID：记录 IPC 错误，本 descriptor 已由 IPC 层消费
  └── OK：获得 descriptor + 完整 anyMSG 指针
          ↓
        出口前 anyMSG 基础校验
          ↓
        选择封包策略
          ├── MTU 足够：encapsulate + send
          └── MTU 不足或接口要求分片：fragment_tx + 顺序 send
          ↓
        成功或失败都释放 Frame Pool block
          ↓
        更新状态和日志
          ↓
        继续处理下一 descriptor
```

## 9. TX Descriptor 处理规则

### 9.1 出队前提

Linux 出口层只能从 `tx_pending_bitmap` 标记或周期扫描发现的 TX Ring 读取 descriptor。直接轮询所有 Ring 可以作为兜底策略，但不得绕过 `linux_shm_dequeue_tx_descriptor()`。

### 9.2 IPC 层校验

以下错误由 `linux_shm_dequeue_tx_descriptor()` 处理，出口 worker 只记录错误和继续下一帧：

| 错误 | IPC 行为 | 出口层行为 |
| ---- | -------- | ---------- |
| TX Ring 为空 | 返回 `UNIFIED_ERR_IPC_QUEUE_EMPTY` | 本轮结束 |
| descriptor CRC 错误 | 消费坏 descriptor，增加 CRC 错误计数 | 记录 IPC CRC 错误 |
| descriptor 格式错误 | 消费坏 descriptor，增加 format 错误计数 | 记录 IPC format 错误 |
| `target_interface` 与 Ring 不一致 | 消费 descriptor | 记录接口错配错误 |
| Frame Pool 引用非法 | 消费 descriptor 或返回错误 | 记录 IPC frame ref 错误 |

### 9.3 出口层二次校验

成功出队后，出口 worker 应检查：

| 检查项 | 规则 |
| ------ | ---- |
| `descriptor.target_interface` | 必须等于当前 worker 的 interface ID |
| `descriptor.frame_length` | 必须 `>= 40` 且 `<= PUT_SHM_FRAME_POOL_BLOCK_SIZE` |
| `msg_length` | 从 anyMSG 头读取后必须等于 `descriptor.frame_length` |
| `payload_length` | 必须满足 `msg_length == 40 + payload_length` |
| 保留字段 | `__RESERVED__`、`__SRCHLD__`、`__PADDING__` 当前必须为 0 |
| CID | `source_cid`、`destination_cid` 首字节必须属于文档定义或保留段 |
| `type` | 允许已定义和保留范围，但不得越界解析 payload |
| epoch | descriptor epoch 必须等于当前 Linux epoch 或被当前 IPC 层判定为可接受 |

出口层二次校验失败时：

1. 不调用物理适配器；
2. 记录 `egress_validate` 错误；
3. 调用 `linux_shm_frame_release()` 释放 Frame Pool block；
4. 继续处理下一 descriptor。

## 10. 封包与发送策略

出口层根据目标接口能力选择直接发送或分片发送。

通用策略：

```text
if adapter get_mtu 足够承载完整 anyMSG:
    adapter.encapsulate(msg, &packet)
    adapter.send(packet)
else:
    adapter.fragment_tx(msg, &packet_list)
    for packet in packet_list:
        adapter.send(packet)
```

实际实现时，如果某个接口虽然 `get_mtu()` 返回完整 block 上限，但适配器内部仍要求私有封包，可以由适配器在 `encapsulate()` 中处理。

### 10.1 发送成功判定

完整 anyMSG 只有在以下条件都满足时，才计为发送成功：

1. 封包或分片成功；
2. 所有需要发送的物理 packet 都返回成功；
3. 没有短写、超时、接口离线或适配器错误；
4. 出口层完成 `status_collector_record_tx_ok()`。

对分片接口，任一分片失败即视为整条 anyMSG 发送失败。

### 10.2 六类接口默认策略

| 接口 | 默认出口策略 |
| ---- | ------------ |
| CAN | 使用 CAN 私有 SOF + DATA 分片协议；按 `can_adapter.fragment_tx()` 输出 `struct can_frame` 序列并顺序 `send()` |
| Ethernet | MTU 足够时直接承载完整 anyMSG；UDP datagram 或 TCP stream 的具体封装由适配器处理 |
| Wi-Fi | 与 Ethernet 相同，默认直接承载完整 anyMSG；无线链路重连由适配器负责 |
| Bluetooth | RFCOMM 流式链路按完整 anyMSG 字节流发送；如后续需要链路私有分片，由 `bluetooth_adapter.fragment_tx()` 承担 |
| 4G | 预留统一接口；可按 TCP/UDP/PPP 数据通道直接承载完整 anyMSG 或由适配器分片 |
| RS485 | 预留统一接口；若物理帧 MTU 小于完整 anyMSG，由 RS485 适配器私有分片 |

### 10.3 顺序与并发

1. 同一接口 TX Ring 内 descriptor 按 ring 出队顺序发送。
2. 同一完整 anyMSG 的分片必须按 `fragment_tx()` 返回顺序发送。
3. 不同物理接口之间允许并发发送。
4. 出口层不跨接口重排小核已经写入的 TX descriptor。
5. 小核调度优先级已经体现在 TX Ring 入队顺序中，出口层不再重排 priority。

## 11. Frame Pool 释放规则

Linux 是 Frame Pool 的唯一最终释放者。出口层必须保证每个成功从 TX Ring 出队的 frame 都走向释放。

### 11.1 TX 出队后的释放

| 场景 | 处理 |
| ---- | ---- |
| 发送成功 | 记录 tx 成功，调用 `linux_shm_frame_release(frame_id, PUT_SHM_RECLAIM_REASON_NONE)` |
| 出口前 anyMSG 校验失败 | 记录错误，释放 frame |
| 接口未启用或离线 | 记录 interface offline / send fail，释放 frame |
| 封包失败 | 记录 encapsulate error，释放 frame |
| 分片失败 | 记录 fragment_tx error，释放 frame |
| 任一 packet 发送失败 | 记录 send fail，释放 frame |
| `linux_shm_frame_release()` 失败 | 记录严重 IPC 错误，触发泄漏可疑统计或后续 Recovery |

发送失败后默认释放失败帧，不退回小核，不进入 RX Ring，不无限重试。

### 11.2 Reclaim Ring 回收

小核消费或丢弃但不转发的 RX_QUEUED frame，会写入 reclaim ring。Linux 统一出口调度器或主循环必须周期处理 reclaim ring。

```text
while linux_shm_dequeue_reclaim_descriptor() == UNIFIED_OK:
    记录 reclaim ack / reason 统计
```

需要回收的典型原因：

| reclaim reason | 场景 |
| -------------- | ---- |
| `HEARTBEAT_CONSUMED` | `type = 0x00` 端到网关心跳被小核消费 |
| `NO_ROUTE` | 小核未找到目标接口 |
| `TTL_EXPIRED` | descriptor TTL 过期 |
| `EPOCH_MISMATCH` | Linux epoch 不匹配 |
| `INVALID_FRAME` | anyMSG 基础校验失败 |
| `QUEUE_FULL` | 小核本地队列或目标 TX Ring 已满 |

reclaim ring 处理失败时，Linux 应记录 IPC 错误，不得静默忽略。若 reclaim 长时间积压，应在 Web 状态中暴露 `reclaim_ring_used` 和 `pending_reclaim`。

## 12. 错误处理策略

出口层错误处理以“不阻塞、不泄漏、可观测”为原则。

| 错误类别 | 处理策略 |
| -------- | -------- |
| TX Ring 空 | 正常结束本轮 worker |
| descriptor CRC / 格式错误 | IPC 层消费，出口层记录错误 |
| Frame Pool 引用非法 | 记录 IPC 错误；无法安全释放时交给 Recovery / sweep |
| anyMSG 二次校验失败 | 不发送，释放 frame，记录 `egress_validate` |
| 接口未启用 | 不发送，释放 frame，记录 `interface_disabled` |
| 接口离线 | 不阻塞等待恢复，释放 frame，记录 `interface_offline` |
| 封包失败 | 释放 frame，记录 `encapsulate` |
| 分片失败 | 释放 frame，记录 `fragment_tx` |
| 短写 / 部分发送 | 视为整帧发送失败，释放 frame，记录 `send_short` |
| 发送超时 | 释放 frame，记录 `send_timeout` |
| `send()` 返回临时拥塞 | 第一版不无限重试，释放 frame，记录 `send_busy` |
| Frame Pool release 失败 | 记录严重 IPC 错误，计入泄漏可疑 |

当前版本不做端到端重试：

1. `retries` 字段保持 anyMSG 帧头原始值，不由出口层递增。
2. 出口层可以在适配器内部做有限链路级重试，但不得改变 anyMSG。
3. 链路级重试失败后仍按发送失败处理并释放 frame。

## 13. 状态统计与 Web 可观测性

出口层必须把状态写入 Linux 状态收集器，由 Web 模块只读展示。

### 13.1 模块统计

每个物理接口至少记录：

| 字段 | 含义 |
| ---- | ---- |
| `tx_frames` | 成功发送的完整 anyMSG 数量 |
| `tx_bytes` | 成功发送的完整 anyMSG 字节数，按 anyMSG 长度计 |
| `send_fail_count` | 物理发送失败数量 |
| `interface_offline_count` | 接口离线导致无法发送数量 |
| `ipc_error_count` | TX dequeue、release 或 reclaim 相关 IPC 错误数量 |
| `last_tx_ms` | 最近一次成功发送时间 |
| `last_error_ms` | 最近一次错误时间 |
| `last_error_stage` | 最近一次错误阶段，例如 `egress_validate`、`fragment_tx`、`send` |
| `last_error_message` | 最近一次错误描述 |

### 13.2 IPC 统计

出口层周期调用 `linux_shm_ipc_get_stats()` 和 `status_collector_update_ipc_stats()`，使 Web 能看到：

1. `tx_pending_bitmap`；
2. 每个 TX Ring 的 used / capacity / enqueue / dequeue / full；
3. Frame Pool used / pending_reclaim / leaked_suspect；
4. reclaim reason 计数；
5. reclaim ring used；
6. descriptor CRC / format 错误；
7. Mailbox notify 和 periodic drain 计数。

### 13.3 日志要求

日志至少包含：

1. 接口名和 interface ID；
2. `frame_id`；
3. `source_cid`、`destination_cid`、`type`；
4. anyMSG 长度；
5. 错误阶段；
6. 错误码；
7. 是否已经释放 Frame Pool block。

日志不得输出敏感 payload 全量内容。需要诊断时可输出 payload 长度、前若干字节摘要或 CRC。

## 14. 推荐实现结构

后续代码实现可采用以下结构，不作为本文强制 ABI：

```text
linux_app/
├── egress/
│   ├── egress_manager.c      # 统一出口调度器、Doorbell / 周期兜底、reclaim drain
│   ├── egress_manager.h
│   ├── egress_worker.c       # 单接口 worker 通用逻辑
│   └── egress_worker.h
└── adapters/
    ├── can_adapter.c
    ├── ethernet_adapter.c
    ├── wifi_adapter.c
    ├── bluetooth_adapter.c
    ├── four_g_adapter.c
    └── rs485_adapter.c
```

建议统一出口上下文字段：

```c
typedef struct {
    put_shm_interface_t interface_id;
    status_module_id_t status_module;
    physical_interface_adapter_t *adapter;
    void *adapter_ctx;
    linux_shm_ipc_t *ipc;
    status_collector_t *collector;
    uint32_t linux_epoch;
    bool enabled;
} egress_worker_context_t;
```

建议统一出口 worker 伪代码：

```c
for (;;) {
    err = linux_shm_dequeue_tx_descriptor(ipc,
                                          interface_id,
                                          &desc,
                                          &frame,
                                          &frame_len);
    if (err == UNIFIED_ERR_IPC_QUEUE_EMPTY) {
        break;
    }
    if (err != UNIFIED_OK) {
        record_ipc_error(err);
        continue;
    }

    send_ok = false;
    if (validate_anymsg_for_egress(frame, frame_len, &desc) == UNIFIED_OK &&
        adapter_is_online(adapter, adapter_ctx)) {
        send_ok = send_by_adapter(adapter, adapter_ctx, frame, frame_len);
    }

    if (send_ok) {
        status_collector_record_tx_ok(collector, status_module, frame_len);
    } else {
        status_collector_record_error(collector, status_module, last_stage, last_err);
    }

    release_err = linux_shm_frame_release(ipc,
                                          desc.frame_id,
                                          PUT_SHM_RECLAIM_REASON_NONE);
    if (release_err != UNIFIED_OK) {
        record_release_error(release_err);
    }
}
```

## 15. 与现有文档的一致性

### 15.1 与统一数据帧设计

本文保持以下约束：

1. anyMSG 固定帧头仍为 40B。
2. `msg_length == 40 + payload_length`。
3. `verify_string[16]` 当前不作为有效业务校验依据。
4. `type` 不决定物理出口。
5. 出口层不改变 anyMSG 帧结构。

### 15.2 与整体架构设计

本文细化《整体架构设计》第 5 节出口层规则：

1. 每个物理接口独立 TX Ring。
2. Linux 根据 `tx_pending_bitmap` 唤醒对应出口执行单元。
3. 出口执行单元从 Frame Pool 读取完整 anyMSG。
4. 适配器负责封包、分片和真实发送。
5. 发送完成或失败后 Linux 释放 Frame Pool。

### 15.3 与共享内存 IPC 设计

本文遵守共享内存 v2：

1. Frame Pool 保存完整 anyMSG。
2. TX Ring 只搬运 descriptor，不内嵌 payload。
3. `tx_pending_bitmap` 是 Ring 状态提示，不是队列计数。
4. Doorbell 只负责唤醒，不传输业务数据。
5. reclaim ring 是小核通知 Linux 回收 RX_QUEUED frame 的唯一闭环。

### 15.4 与 FreeRTOS 小核设计

本文保持小核边界：

1. 小核只写目标 TX Ring，不执行真实发送。
2. 小核不释放 Frame Pool。
3. 小核消费或丢弃的帧必须写 reclaim ring。
4. Linux 出口层不改变小核已完成的路由结果。

### 15.5 与 CAN 模块设计

本文保持 CAN 出口规则：

1. CAN adapter 只从 CAN TX Ring 读取小核已经路由到 CAN 的 descriptor。
2. CAN ID 只用于物理链路仲裁、过滤和诊断，不参与业务路由。
3. Classic CAN 使用私有 SOF + DATA 分片协议承载完整 anyMSG。
4. 发送失败后由 Linux 出口层释放 Frame Pool block。

## 16. 测试与验收场景

后续实现统一出口层时，至少覆盖以下测试：

| 场景 | 预期结果 |
| ---- | -------- |
| TX Ring 有合法 descriptor | 出队、发送、记录 tx、释放 Frame Pool |
| TX Ring 为空 | worker 正常退出本轮，无错误 |
| descriptor CRC 错误 | IPC 层消费 descriptor，统计 CRC 错误，worker 继续 |
| `target_interface` 错配 | IPC 层拒绝并消费，统计 format 错误 |
| anyMSG 长度非法 | 不发送，释放 frame，记录 `egress_validate` |
| 接口未启用 | 不发送，释放 frame，记录 `interface_disabled` |
| 接口离线 | 不阻塞，释放 frame，记录 `interface_offline` |
| CAN 分片全部成功 | 按 SOF + DATA 顺序发送，整帧计 tx 成功 |
| CAN 任一分片失败 | 整帧计发送失败，释放 frame |
| Ethernet/Wi-Fi 直接发送成功 | 完整 anyMSG 作为物理载荷发送，释放 frame |
| Bluetooth 流式发送短写 | 计发送失败，释放 frame |
| Doorbell 丢失 | 100ms 周期 drain 发现 pending 并发送 |
| pending bit 清除竞态 | 同接口或跨接口新入队不丢 pending |
| reclaim ring 有心跳消费 descriptor | Linux 回收 Frame Pool，统计 `HEARTBEAT_CONSUMED` |
| reclaim ring 有无路由 descriptor | Linux 回收 Frame Pool，统计 `NO_ROUTE` |
| release 失败 | 记录严重 IPC 错误和泄漏可疑 |

建议回归现有 IPC 测试：

```text
linux_shm_dequeue_tx_descriptor()
linux_shm_frame_release()
linux_shm_dequeue_reclaim_descriptor()
pending bitmap clear / set 竞态
descriptor CRC / format error
Frame Pool 状态机
```

## 17. 第一版默认策略

第一版统一出口层默认策略如下：

| 策略项 | 默认值 |
| ------ | ------ |
| 周期兜底 drain | `100ms` |
| 单 worker 每轮 descriptor 预算 | `16` |
| anyMSG 最大发送长度 | `PUT_SHM_FRAME_POOL_BLOCK_SIZE = 512B` |
| 端到端重试 | 不启用 |
| 发送失败处理 | 记录错误并释放 frame |
| TX Ring 顺序 | 保持 ring 出队顺序 |
| 分片发送顺序 | 保持 `fragment_tx()` 返回顺序 |
| reclaim drain | 与出口调度器周期执行，或主循环每轮执行 |
| Web 访问 | 只读 Linux 状态快照和日志 |

这些默认策略不写入 anyMSG 帧头，不改变共享内存 ABI，可由后续配置文件或适配器私有配置细化。
