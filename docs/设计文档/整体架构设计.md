# 多协议统一终端仓库设计

## 1. 仓库设计原则

本项目建议采用 **monorepo 单仓库结构** 管理。

原因是本项目中大核 Linux、小核 RTOS、C51 低功耗控制、Web 监控展示、统一协议帧、共享内存通信、硬件连接文档之间关系非常紧密。如果拆成多个仓库，后期修改统一协议、调试大小核共享内存通信、查看系统状态、整理比赛材料时会比较混乱。

项目整体主线如下：

```text
多协议输入 → 大核 Linux 统一封装 → 共享内存通信 → 小核 RTOS 实时 CAN 转发 → C51 低功耗唤醒管理
                         ↓
                  Web 监控展示与日志查看
```

也可以理解为：

```text
4G / WiFi / 蓝牙 / RS485 / 以太网
        ↓
大核 Linux 协议适配层
        ├── Web 监控展示
        │      ├── 模块连通性
        │      ├── 系统资源占用
        │      └── 系统日志
        ↓
统一数据帧 unified_frame
        ↓
共享内存通信
        ↓
小核 RTOS 实时 CAN 发送
        ↓
CAN 总线设备
```

## 3. 总体架构逻辑

本项目不要把“4G 转 CAN、WiFi 转 CAN、蓝牙转 CAN、RS485 转 CAN、以太网转 CAN”写成完全独立的程序。

应该抽象为：

```text
外部协议适配层 → 内部统一帧 unified_frame_t → 共享内存通信 → 小核实时 CAN 发送
```

具体流程为：

```text
4G
WiFi
Bluetooth
RS485
Ethernet
   ↓
大核 Linux 解析不同协议
   ↓
统一封装成 unified_frame
   ↓
写入共享内存并通知小核 RTOS
   ↓
小核按实时要求发送到 CAN 总线
```

Web 模块不改变主通信链路，它运行在大核 Linux 侧，用于读取和展示系统状态。Web 后端可以直接读取系统资源、设备存在性和日志文件；协议连通性、收发计数、解析错误、大小核通信状态等业务状态由 `linux_app` 生成 JSON 快照后供 Web 只读展示。Web 不直接解析外部协议，不读取统一帧 ring，也不向小核发送控制命令。

当前业务中外部输入不会是 anyMSG，因此主流程不设计“外部数据 → anyMSG → unified_frame_t”这一层。

大核收到 UDP、RS485、蓝牙自定义数据、MQTT/云端数据等输入后，由对应协议适配器提取 CAN 字段，再封装为 `unified_frame_t`。

老师 anyMSG 资料只作为业务类型和 payload 语义参考；`unified_frame_t` 才是大核到小核之间的项目内部必经协议。

因此，仓库中最核心的公共文件是：

```text
common/include/unified_frame.h
```

它定义大核和小核之间传输的统一数据格式。

### 3.1 大小核通信方式：共享内存

本项目的大核 Linux 和小核 RTOS 通过 **共享内存** 传递业务数据，不再把“大核到小核”理解成串口、SPI 或普通网络通信。

共享内存通道只传递项目内部统一帧：

```text
大核 Linux
  ↓ 写入 unified_frame_t
共享内存环形队列
  ↓ 小核读取 unified_frame_t
小核 RTOS
```

推荐通信流程：

```text
大核协议适配层收到外部数据
  ↓
frame_packer 打包为 unified_frame_t
  ↓
ipc_to_rtos 写入共享内存 TX 环形队列
  ↓
刷新 cache / 内存屏障
  ↓
通过中断、mailbox 或 doorbell 标志通知小核
  ↓
小核 ipc_rx_task 从共享内存读取 unified_frame_t
  ↓
校验 magic、version、length、CRC
  ↓
放入 CAN 发送队列
```

共享内存设计要点：

- 共享内存地址和长度需要在 Linux 设备树 `reserved-memory` 与小核 RTOS linker script / BSP 中保持一致；
- 共享内存中不要存放普通指针，只存放固定长度结构体、偏移量、读写索引和状态标志；
- 大核到小核建议采用单生产者、单消费者环形队列；
- `write_index` 由大核更新，`read_index` 由小核更新，避免双方同时写同一个字段；
- 如果共享内存区域可缓存，写入方需要 cache flush，读取方需要 cache invalidate；
- 读写索引和状态标志需要配合 `volatile`、atomic 或内存屏障，避免乱序访问；
- 可选增加“小核到大核”的 ACK / 状态环形队列，用于上报发送成功、发送失败、队列满、CRC 错误等状态。

逻辑上可以把共享内存划分为：

```text
shared_memory_region
├── header                 # magic、version、通道状态
├── linux_to_rtos_queue    # 大核写，小核读
└── rtos_to_linux_queue    # 可选，小核写，大核读，用于 ACK / 状态上报
```

共享内存队列建议只保存固定大小的帧槽位：

```c
#define SHM_FRAME_QUEUE_DEPTH 32

typedef struct {
    volatile uint32_t write_index;   // 写入方更新
    volatile uint32_t read_index;    // 读取方更新
    volatile uint32_t drop_count;    // 队列满等异常统计
    unified_frame_t frames[SHM_FRAME_QUEUE_DEPTH];
} shm_frame_queue_t;
```

## 4. common 公共层设计

`common/` 目录用于存放大核和小核都需要使用的公共代码。

```text
common/
├── include/
│   ├── unified_frame.h
│   ├── shared_memory_ipc.h
│   ├── protocol_type.h
│   └── error_code.h
└── src/
```

建议 `common/` 只放稳定的公共内容，例如：

- 统一帧格式
- 共享内存通道数据结构
- 协议类型枚举
- 错误码
- CRC 校验函数
- 公共宏定义

不要把某个具体业务协议放到 `common/` 里面。

例如：

```text
wifi_server.c
rs485_can_direct.c
four_g_client.c
```

这些只属于大核 Linux 应用，不应该放到 `common/`。

## 5. 统一协议帧示例

`common/include/unified_frame.h` 可以先这样设计：

```c
#ifndef UNIFIED_FRAME_H
#define UNIFIED_FRAME_H

#include <stdint.h>

#define UNIFIED_FRAME_MAGIC 0xA55A
#define UNIFIED_DATA_MAX_LEN 64

typedef enum {
    PROTOCOL_4G = 0x01,
    PROTOCOL_WIFI = 0x02,
    PROTOCOL_BLUETOOTH = 0x03,
    PROTOCOL_RS485 = 0x04,
    PROTOCOL_ETHERNET = 0x05,
} protocol_type_t;

typedef struct {
    uint16_t magic;              // 帧头
    uint8_t  protocol_type;      // 来源协议类型
    uint8_t  frame_type;         // 数据帧 / 控制帧 / 心跳帧
    uint32_t can_id;             // 要发送到 CAN 的 ID
    uint8_t  can_dlc;            // CAN 数据长度
    uint8_t  data[UNIFIED_DATA_MAX_LEN];
    uint16_t crc;                // 校验
} unified_frame_t;

#endif
```

这个结构体就是大核和小核之间通过共享内存通信时承载的核心协议。

大核只需要把不同协议的数据统一打包成 `unified_frame_t`，写入共享内存环形队列；小核只需要从共享内存读取并解析 `unified_frame_t`，再发送到 CAN。

## 6. 大核 Linux 应用设计

大核负责复杂协议处理和非实时任务。

大核主要职责：

- 4G 通信处理
- WiFi 通信处理
- 蓝牙通信处理
- RS485 / Modbus 通信处理
- 以太网 TCP / UDP 通信处理
- USB 设备识别与管理
- 配置文件读取
- 日志记录
- 模块状态采集
- 协议解析
- 统一数据帧打包
- 通过共享内存发送数据给小核
- 向 Web 模块提供协议业务状态快照和日志数据

```text

└── drivers/
    ├── uart_linux.c
    ├── usb_device.c

```

大核程序主流程：

```text
main.c
  ↓
初始化配置
  ↓
启动 4G / WiFi / 蓝牙 / RS485 / 以太网接收任务
  ↓
启动协议业务状态快照和日志记录
  ↓
不同协议收到数据
  ↓
调用 frame_packer 打包为 unified_frame
  ↓
调用 ipc_to_rtos 写入共享内存并通知小核
```

大核不要直接操作 CAN。

大核只负责：

```text
不同协议数据 → 统一帧 → 共享内存 TX 队列
协议业务状态 / 系统日志 → Web 展示数据
```

## 7. Web 监控展示模块设计

Web 模块用于比赛演示、现场调试和系统运维查看，建议作为大核 Linux 上的独立轻量服务运行。后端使用 Rust + Axum/Tokio，实现为 `put-webd` 单个静态交叉编译可执行程序；前端使用 Vue3 + Vite，构建后的 `dist/` 作为外置静态文件由后端托管。

Web 模块主要展示：

- 4G、WiFi、蓝牙、以太网、RS485、CAN、大小核通信的连通性
- 每个协议模块的接收计数、发送计数、错误计数和最近通信时间
- 小核 RTOS 回传的 CAN 总线状态、发送失败次数、总线错误状态
- CPU 使用率、内存占用、磁盘空间、网络收发速率、系统运行时间
- 大核应用日志、协议解析日志、CAN 异常日志、系统启动日志
- 关键异常告警，例如模块断连、长时间无数据、CRC 错误、IPC 超时等

推荐目录：

```text
web/
├── README.md
├── backend/
│   ├── Cargo.toml
│   └── src/
│       ├── main.rs
│       ├── api.rs
│       ├── status_snapshot.rs
│       ├── system_reader.rs
│       └── log_reader.rs
├── frontend/
│   ├── package.json
│   ├── src/
│   └── dist/
└── config/
    └── web_config.toml
```

Web 后端建议提供只读接口：

```text
GET /api/health       # Web 服务健康状态
GET /api/modules      # 各协议模块连通性和收发统计
GET /api/resources    # CPU/内存/磁盘/网络占用
GET /api/can-status   # CAN 总线和小核回传状态
GET /api/ipc-status   # 大小核通信状态
GET /api/logs         # 系统日志查询
GET /api/events       # 最近异常事件
```

Web 数据来源采用混合分工：

```text
系统资源 / 设备存在性 / 日志文件
  ↓
Web 后端直接读取 /proc /sys /dev /var/log/put

协议连通性 / 收发计数 / 解析错误 / IPC 与 CAN 状态
  ↓
linux_app 维护状态并写入 /run/put/status/*.json
  ↓
web/backend/status_snapshot.rs 只读快照
  ↓
浏览器监控页面
```

`linux_app` 不提供 Web API，也不负责 Vue 页面；它只维护业务状态计数、最近错误和事件记录，并周期写入 `/run/put/status/`。系统资源采集、设备存在性检查、日志分页读取由 Rust Web 后端完成。

系统日志建议由 `linux_app/log_manager` 统一写入 `/var/log/put/`，Web 模块只负责分页读取、按等级过滤和关键字搜索。第一版以局域网只读展示为主，不提供登录、写接口或高风险控制操作。

## 8. 小核 RTOS 固件设计

小核负责实时性任务，尤其是 CAN 发送。

小核主要职责：

- 从共享内存读取大核写入的统一数据帧
- 校验帧头、长度、CRC
- 解析 CAN ID、DLC、数据区
- 按实时要求发送 CAN 报文
- 处理 CAN 发送队列
- 看门狗与异常保护

推荐目录：

```text
rtos_firmware/
├── main.c
├── src/
│   ├── ipc_rx_task.c        # 共享内存读取、索引更新、异常统计
│   ├── frame_parser.c
│   ├── can_task.c
│   ├── can_driver.c
│   └── watchdog.c
└── bsp/
    ├── board.c
    ├── clock.c
    ├── pinmux.c
    └── interrupt.c
```

小核主流程：

```text
ipc_rx_task 从共享内存读取 unified_frame
  ↓
frame_parser 检查帧头、长度、CRC
  ↓
放入 CAN 发送队列
  ↓
can_task 按优先级 / 周期 / 实时要求发送到 CAN 总线
```

小核不应该关心这些内容：

```text
4G 是怎么来的
WiFi 是怎么来的
蓝牙连接谁
TCP 怎么握手
CAN direct 怎么分帧和校验
```

小核只需要识别：

```text
unified_frame_t
```

## 11. tools 调试工具目录设计

## 14. 分支管理建议

前期比赛项目不需要太复杂，建议使用：

```text
main        # 稳定版本
develop     # 日常开发版本
feature/xxx # 功能开发分支
```

示例：

```text
feature/rs485-to-can
feature/wifi-to-can
feature/bluetooth-to-can
feature/4g-to-can
feature/low-power
feature/rtos-can-send
feature/web-monitor
```

推荐开发流程：

```text
个人在 feature 分支开发
  ↓
测试通过
  ↓
合并到 develop
  ↓
阶段性稳定后
  ↓
合并到 main
```

不要所有人都直接往 `main` 分支提交代码。

## 17. 最终职责划分总结

```text
docs/              给老师、队友、答辩看的文档
common/            大核小核都要用的公共协议和工具
linux_app/         大核 Linux 程序
web/               Web 监控展示模块
rtos_firmware/     小核 RTOS 实时程序
c51_low_power/     C51 低功耗唤醒程序
tools/             调试工具
scripts/           构建、烧录、打包脚本
tests/             测试代码
third_party/       第三方库
```

最核心的设计原则：

```text
大核负责复杂通信
Web 负责状态展示
小核负责实时 CAN
C51 负责低功耗唤醒
common 负责统一协议和共享内存通道数据结构
docs 负责项目说明
```

项目主线必须保持清楚：

```text
多协议输入 → 大核统一封装 → 共享内存通信 → 小核实时转 CAN → C51 低功耗管理
                       ↓
                Web 监控展示与日志查看
```
