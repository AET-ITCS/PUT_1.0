# 多协议统一终端仓库设计

## 1. 仓库设计原则

本项目建议采用 **monorepo 单仓库结构** 管理。

原因是本项目中大核 Linux、小核 RTOS、C51 低功耗控制、Web 监控展示、统一协议帧、硬件连接文档之间关系非常紧密。如果拆成多个仓库，后期修改统一协议、调试大小核通信、查看系统状态、整理比赛材料时会比较混乱。

项目整体主线如下：

```text
多协议输入 → 大核 Linux 统一封装 → 大小核通信 → 小核 RTOS 实时 CAN 转发 → C51 低功耗唤醒管理
                         ↓
                  Web 监控展示与日志查看
```

也可以理解为：

```text
4G / WiFi / 蓝牙 / RS485 / 以太网
        ↓
大核 Linux 协议适配层
        ├── Web 监控展示
        │      ├── 模块连通性
        │      ├── 系统资源占用
        │      └── 系统日志
        ↓
统一数据帧 unified_frame
        ↓
大小核通信
        ↓
小核 RTOS 实时 CAN 发送
        ↓
CAN 总线设备
```

## 3. 总体架构逻辑

本项目不要把“4G 转 CAN、WiFi 转 CAN、蓝牙转 CAN、RS485 转 CAN、以太网转 CAN”写成完全独立的程序。

应该抽象为：

```text
外部协议适配层 → 内部统一帧 unified_frame_t → 大小核通信 → 小核实时 CAN 发送
```

具体流程为：

```text
4G
WiFi
Bluetooth
RS485
Ethernet
   ↓
大核 Linux 解析不同协议
   ↓
统一封装成 unified_frame
   ↓
发送给小核 RTOS
   ↓
小核按实时要求发送到 CAN 总线
```

Web 模块不改变主通信链路，它运行在大核 Linux 侧，用于读取和展示系统状态。它应从大核状态缓存、大小核状态回传、日志文件或本地进程接口中取数，不直接接管 CAN 实时发送逻辑。

当前业务中外部输入不会是 anyMSG，因此主流程不设计“外部数据 → anyMSG → unified_frame_t”这一层。

大核收到 Modbus、普通 TCP/UDP 私有帧、蓝牙自定义数据、MQTT/云端数据等输入后，由对应协议适配器直接提取业务命令，再封装为 `unified_frame_t`。

老师 anyMSG 资料只作为业务类型和 payload 语义参考；`unified_frame_t` 才是大核到小核之间的项目内部必经协议。

因此，仓库中最核心的公共文件是：

```text
common/include/unified_frame.h
```

它定义大核和小核之间传输的统一数据格式。

## 4. common 公共层设计

`common/` 目录用于存放大核和小核都需要使用的公共代码。

```text
common/
├── include/
│   ├── unified_frame.h
│   ├── protocol_type.h
│   ├── error_code.h
│   └── ring_buffer.h
└── src/
    └── ring_buffer.c
```

建议 `common/` 只放稳定的公共内容，例如：

- 统一帧格式
- 协议类型枚举
- 错误码
- CRC 校验函数
- 环形缓冲区
- 公共宏定义

不要把某个具体业务协议放到 `common/` 里面。

例如：

```text
wifi_server.c
rs485_modbus.c
four_g_client.c
```

这些只属于大核 Linux 应用，不应该放到 `common/`。

## 5. 统一协议帧示例

`common/include/unified_frame.h` 可以先这样设计：

```c
#ifndef UNIFIED_FRAME_H
#define UNIFIED_FRAME_H

#include <stdint.h>

#define UNIFIED_FRAME_MAGIC 0xA55A
#define UNIFIED_DATA_MAX_LEN 64

typedef enum {
    PROTOCOL_4G = 0x01,
    PROTOCOL_WIFI = 0x02,
    PROTOCOL_BLUETOOTH = 0x03,
    PROTOCOL_RS485 = 0x04,
    PROTOCOL_ETHERNET = 0x05,
} protocol_type_t;

typedef struct {
    uint16_t magic;              // 帧头
    uint8_t  protocol_type;      // 来源协议类型
    uint8_t  frame_type;         // 数据帧 / 控制帧 / 心跳帧
    uint32_t can_id;             // 要发送到 CAN 的 ID
    uint8_t  can_dlc;            // CAN 数据长度
    uint8_t  data[UNIFIED_DATA_MAX_LEN];
    uint16_t crc;                // 校验
} unified_frame_t;

#endif
```

这个结构体就是大核和小核之间通信的核心协议。

大核只需要把不同协议的数据统一打包成 `unified_frame_t`，小核只需要解析 `unified_frame_t` 并发送到 CAN。

## 6. 大核 Linux 应用设计

大核负责复杂协议处理和非实时任务。

大核主要职责：

- 4G 通信处理
- WiFi 通信处理
- 蓝牙通信处理
- RS485 / Modbus 通信处理
- 以太网 TCP / UDP 通信处理
- USB 设备识别与管理
- 配置文件读取
- 日志记录
- 模块状态采集
- 系统资源采集
- 协议解析
- 统一数据帧打包
- 发送数据给小核
- 向 Web 模块提供状态和日志数据

推荐目录：

```text
linux_app/
├── main.c
├── src/
│   ├── protocol_manager.c
│   ├── frame_packer.c
│   ├── ipc_to_rtos.c
│   ├── status_collector.c
│   ├── resource_monitor.c
│   ├── log_manager.c
│   └── config.c
├── protocols/
│   ├── rs485_modbus.c
│   ├── ethernet_tcp.c
│   ├── wifi_server.c
│   ├── bluetooth_server.c
│   └── four_g_client.c
└── drivers/
    ├── uart_linux.c
    ├── usb_device.c
    └── gpio_linux.c
```

大核程序主流程：

```text
main.c
  ↓
初始化配置
  ↓
启动 4G / WiFi / 蓝牙 / RS485 / 以太网接收任务
  ↓
启动状态采集和日志记录
  ↓
不同协议收到数据
  ↓
调用 frame_packer 打包为 unified_frame
  ↓
调用 ipc_to_rtos 发送给小核
```

大核不要直接操作 CAN。

大核只负责：

```text
不同协议数据 → 统一帧
运行状态 / 系统日志 → Web 展示数据
```

## 7. Web 监控展示模块设计

Web 模块用于比赛演示、现场调试和系统运维查看，建议作为大核 Linux 上的独立轻量服务运行。

Web 模块主要展示：

- 4G、WiFi、蓝牙、以太网、RS485、CAN、大小核通信的连通性
- 每个协议模块的接收计数、发送计数、错误计数和最近通信时间
- 小核 RTOS 回传的 CAN 总线状态、发送失败次数、总线错误状态
- CPU 使用率、内存占用、磁盘空间、网络收发速率、系统运行时间
- 大核应用日志、协议解析日志、CAN 异常日志、系统启动日志
- 关键异常告警，例如模块断连、长时间无数据、CRC 错误、IPC 超时等

推荐目录：

```text
web/
├── README.md
├── backend/
│   ├── web_server.c
│   ├── status_api.c
│   ├── resource_api.c
│   └── log_reader.c
├── frontend/
│   ├── index.html
│   ├── css/
│   └── js/
└── config/
    └── web_config.json
```

Web 后端建议提供只读接口：

```text
GET /api/health       # Web 服务健康状态
GET /api/modules      # 各协议模块连通性和收发统计
GET /api/resources    # CPU/内存/磁盘/网络占用
GET /api/can_status   # CAN 总线和小核回传状态
GET /api/logs         # 系统日志查询
GET /api/events       # 最近异常事件
```

Web 数据来源建议如下：

```text
协议模块运行状态
  ↓
linux_app/status_collector
  ↓
本地状态缓存 / Unix Socket / 本地 HTTP API
  ↓
web/backend/status_api
  ↓
浏览器监控页面
```

系统日志建议由 `linux_app/log_manager` 统一写入文件，Web 模块只负责分页读取、按等级过滤和关键字搜索。第一版以只读展示为主，不在 Web 页面上直接提供高风险控制操作。

## 8. 小核 RTOS 固件设计

小核负责实时性任务，尤其是 CAN 发送。

小核主要职责：

- 接收大核发送的统一数据帧
- 校验帧头、长度、CRC
- 解析 CAN ID、DLC、数据区
- 按实时要求发送 CAN 报文
- 处理 CAN 发送队列
- 看门狗与异常保护

推荐目录：

```text
rtos_firmware/
├── main.c
├── src/
│   ├── ipc_rx_task.c
│   ├── frame_parser.c
│   ├── can_task.c
│   ├── can_driver.c
│   └── watchdog.c
└── bsp/
    ├── board.c
    ├── clock.c
    ├── pinmux.c
    └── interrupt.c
```

小核主流程：

```text
ipc_rx_task 接收大核发来的 unified_frame
  ↓
frame_parser 检查帧头、长度、CRC
  ↓
放入 CAN 发送队列
  ↓
can_task 按优先级 / 周期 / 实时要求发送到 CAN 总线
```

小核不应该关心这些内容：

```text
4G 是怎么来的
WiFi 是怎么来的
蓝牙连接谁
TCP 怎么握手
Modbus 怎么解析
```

小核只需要识别：

```text
unified_frame_t
```

## 9. C51 低功耗程序设计

C51 单独作为低功耗唤醒控制模块。

推荐目录：

```text
c51_low_power/
├── main.c
├── wakeup.c
├── power_ctrl.c
└── README.md
```

C51 主要职责：

```text
检测外部唤醒信号
  ↓
控制 Milk-V Duo256M 上电 / 唤醒
  ↓
检测系统空闲状态
  ↓
控制系统进入低功耗
```

C51 不参与协议转换，也不参与 CAN 数据发送。

它只负责电源状态管理和唤醒控制。

```text
  ↓
合并到 develop
  ↓
阶段性稳定后
  ↓
合并到 main
```

不要所有人都直接往 `main` 分支提交代码。

```gitignore

output/

!.vscode/launch.json

*.log

# Python
__pycache__/

# OS
```

如果 VS Code 配置是团队共用的，可以保留：

```text
.vscode/tasks.json
```

```text

```

这种路径不适合提交到公共仓库中。

## 17. 最终职责划分总结

```text
docs/              给老师、队友、答辩看的文档
common/            大核小核都要用的公共协议和工具
linux_app/         大核 Linux 程序
web/               Web 监控展示模块
rtos_firmware/     小核 RTOS 实时程序
c51_low_power/     C51 低功耗唤醒程序
tools/             调试工具
scripts/           构建、烧录、打包脚本
tests/             测试代码
third_party/       第三方库
```

最核心的设计原则：

```text
大核负责复杂通信
Web 负责状态展示
小核负责实时 CAN
C51 负责低功耗唤醒
common 负责统一协议
docs 负责项目说明
```

项目主线必须保持清楚：

```text
多协议输入 → 大核统一封装 → 小核实时转 CAN → C51 低功耗管理
                       ↓
                Web 监控展示与日志查看
```
