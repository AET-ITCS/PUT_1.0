# 多协议 anyMSG 网关整体架构设计

版本号：0.2.1
修改时间：2026-05-25
文档定位：系统总体架构、模块职责、接入/出口、共享内存和调度设计

---

## 1. 架构原则

本项目采用 **monorepo 单仓库结构** 管理大核 Linux、小核 FreeRTOS、Web 监控、C51 低功耗控制、统一数据帧、共享内存 IPC、测试工具和项目文档。

目标架构以完整 anyMSG 作为统一业务帧。外部设备把完整 anyMSG 放入物理协议载荷中；Linux 大核负责真实物理收发、解包/封包和分片/重组；FreeRTOS 小核只负责共享内存中的完整 anyMSG 路由、队列调度和实时控制；Linux 出口层再负责真实发送。

系统主链路如下：

```text
外部设备
  ↓ 完整 anyMSG 放入物理协议载荷，必要时分片
Linux 大核接入层
  ↓ 解包 / 重组 / 校验出完整 anyMSG
共享内存 RX Ring + Frame Pool
  ↓ Mailbox Doorbell 唤醒
FreeRTOS 小核路由调度
  ↓ anyMSG 头部校验 / 心跳消费 / 路由 / 优先级调度
共享内存 TX Ring + Frame Pool
  ↓ Mailbox Doorbell 通知
Linux 大核出口层
  ↓ 按目标物理接口封包 / 分片 / 发送
目标设备
```

物理接口固定为六类：

```text
CAN / Ethernet / Wi-Fi / Bluetooth / 4G / RS485
```

Web 模块不改变主通信链路，只读取 Linux 生成的状态快照、系统资源和日志。C51 不参与协议转换，只负责低功耗和唤醒控制。

## 3. 总体职责边界

| 模块          | 负责                                                                            | 不负责                           |
| ------------- | ------------------------------------------------------------------------------- | -------------------------------- |
| Linux 接入层  | 六类物理接口监听、协议解包、分片重组、完整 anyMSG 校验、写共享内存 RX Ring      | 小核路由调度                     |
| FreeRTOS 小核 | 共享内存 RX Ring drain、anyMSG 头部校验、心跳消费、路由、优先级调度、写 TX Ring | 真实 CAN/RS485/网络/蓝牙/4G 收发 |
| Linux 出口层  | 读 TX Ring、目标协议封包、必要时分片、真实物理发送                              | 修改小核路由结果                 |
| 共享内存 IPC  | Frame Pool、Descriptor Ring、Pending Bitmap、cache 同步、Mailbox Doorbell       | 解释具体业务 payload             |
| Web 模块      | 只读展示状态、资源、日志和异常事件                                              | 直接读写共享内存或控制物理接口   |
| C51 低功耗    | 上电、唤醒、低功耗控制                                                          | 协议转换和数据转发               |

核心原则：

```text
Linux 负责真实物理收发和协议差异；
小核负责共享内存中的完整 anyMSG 路由和调度；
Mailbox 只负责唤醒，不传输业务数据；
共享内存是大小核之间唯一业务数据通道。
```

## 4. 接入层设计

接入层为六类物理接口分别提供适配器。

```text
CAN RX
Ethernet RX
Wi-Fi RX
Bluetooth RX
4G RX
RS485 RX
   ↓
接口适配器 decode / reassemble
   ↓
完整 anyMSG
   ↓
共享内存 Frame Pool
   ↓
对应物理接口 RX Ring 描述符
   ↓
RX Pending Bitmap + Mailbox Doorbell
```

### 4.1 线程模型

接入层必须做到每个接口独立队列、独立状态、独立重组缓存、独立故障统计，但不要求每个接口一定对应一个系统线程。

| 接口类型                                    | 推荐执行模型                              |
| ------------------------------------------- | ----------------------------------------- |
| 阻塞式串口、蓝牙 RFCOMM、4G AT/PPP 数据通道 | 独立 RX 线程                              |
| UDP/TCP socket、CAN raw socket              | 可使用独立线程，也可并入 epoll/event loop |
| 高吞吐或高实时压力接口                      | 独立线程或独立 event loop                 |

无论采用线程还是 event loop，都必须满足：

1. 一个接口阻塞、断连或重组超时不能影响其他接口；
2. 每个接口都有自己的 RX Ring；
3. 每个接口都有自己的重组缓存；
4. 每个接口都有独立统计；
5. 写共享内存前必须已经得到完整 anyMSG。

## 5. 出口层设计

出口层为六类物理接口分别提供发送队列。

```text
小核路由完成
   ↓
目标物理接口 TX Ring 描述符
   ↓
TX Pending Bitmap + Mailbox Doorbell
   ↓
Linux 出口执行单元
   ↓
读取 Frame Pool 中完整 anyMSG
   ↓
接口适配器 encapsulate / fragment_tx
   ↓
CAN / Ethernet / Wi-Fi / Bluetooth / 4G / RS485 真实发送
```

出口层规则：

1. 每个物理接口独立 TX Ring。
2. Linux 收到小核 Doorbell 后读取 TX Pending Bitmap。
3. Linux 只唤醒有 pending 的出口执行单元。
4. 出口执行单元从对应 TX Ring 读取描述符，再从 Frame Pool 读取完整 anyMSG。
5. 如果目标协议 MTU 足够，直接封包发送。
6. 如果目标协议 MTU 不足，出口适配器执行分片发送。
7. 发送完成或失败后，Linux 负责释放 Frame Pool 中的帧资源，并更新统计。

## 6. 大帧与分片重组

不同物理协议可承载的单帧载荷不同。例如 CAN classic、部分串口协议或蓝牙流式协议无法一次承载较大的 anyMSG。因此分片重组必须放在物理接口适配层，而不是放在小核路由层。

设计原则：

1. 外部链路可以分片承载 anyMSG。
2. Linux 接入层必须重组出完整 anyMSG 后，才能写共享内存 RX Ring。
3. 小核永远只处理完整 anyMSG，不处理 anyMSG 分片。
4. Linux 出口层根据目标接口 MTU 决定是否分片发送。
5. 分片头是物理适配层封装的一部分，不属于 anyMSG 帧头。

统一分片头建议字段：

| 字段           | 作用                            |
| -------------- | ------------------------------- |
| `session_id`   | 一次 anyMSG 分片传输的会话 ID   |
| `total_len`    | 完整 anyMSG 总长度              |
| `offset`       | 当前分片在完整 anyMSG 中的偏移  |
| `fragment_len` | 当前分片 payload 长度           |
| `seq`          | 分片序号                        |
| `flags`        | 首片、尾片、是否需要 ACK 等标志 |
| `crc16`        | 当前分片或完整帧校验            |
| `timeout_ms`   | 重组超时策略参数                |

接入层重组异常处理：

| 异常                 | 处理                                   |
| -------------------- | -------------------------------------- |
| 丢片                 | 等待超时后释放重组缓存，记录 drop      |
| 重复片               | 忽略重复数据，记录 duplicate           |
| 乱序                 | 按 `offset` 重组，不要求顺序到达       |
| CRC 错误             | 丢弃对应分片或整帧，记录 crc error     |
| `total_len` 超过上限 | 立即拒绝，记录 oversized               |
| 重组缓存耗尽         | 丢弃低优先级或最新会话，记录 no buffer |

## 7. 协议适配器接口

各协议的解包和封包差异很大，不能把差异写进共享内存层或小核路由层。目标架构采用接口适配器表隔离差异。

建议适配器接口如下：

```c
typedef struct {
    const char *name;
    uint8_t interface_id;

    size_t (*get_mtu)(void *ctx);

    int (*decode_rx)(void *ctx,
                     const uint8_t *input,
                     size_t input_len,
                     adapter_rx_result_t *out);

    int (*reassemble)(void *ctx,
                      const adapter_fragment_t *fragment,
                      anymsg_buffer_t *out_complete_msg);

    int (*encapsulate)(void *ctx,
                       const anymsg_buffer_t *msg,
                       adapter_tx_packet_t *out_packet);

    int (*fragment_tx)(void *ctx,
                       const anymsg_buffer_t *msg,
                       adapter_tx_packet_list_t *out_packets);

    int (*send)(void *ctx,
                const adapter_tx_packet_t *packet);

    int (*status)(void *ctx,
                  adapter_status_t *out_status);
} physical_interface_adapter_t;
```

接口边界：

| 层级           | 负责内容                                                   |
| -------------- | ---------------------------------------------------------- |
| 物理接口适配器 | 协议私有头、流式分帧、分片重组、MTU、发送封包              |
| anyMSG 公共层  | anyMSG 头部解析、长度校验、CID 读取、type 读取             |
| 共享内存层     | Frame Pool 分配释放、描述符 Ring、cache 同步、Mailbox 通知 |
| 小核路由层     | 心跳消费、目的地址路由、优先级调度、TX Ring 分发           |

新增协议时只需要新增一个适配器，不需要改动小核路由核心。

## 8. 共享内存 v2 设计

目标架构中的共享内存不再把完整业务帧塞进固定 128B slot，而是使用：

```text
Frame Pool          # 保存完整 anyMSG 字节
Descriptor RX Ring  # Linux 写，小核读
Descriptor TX Ring  # 小核写，Linux 读
Pending Bitmap      # 表示哪些 Ring 非空
Mailbox Doorbell    # 只做唤醒，不传输数据
```

建议共享内存结构：

```text
shared_memory_region_v2
├── region_header
├── frame_pool
│   ├── frame_buffer[0]
│   ├── frame_buffer[1]
│   └── ...
├── rx_rings
│   ├── CAN_RX_RING
│   ├── ETH_RX_RING
│   ├── WIFI_RX_RING
│   ├── BT_RX_RING
│   ├── LTE_RX_RING
│   └── RS485_RX_RING
├── tx_rings
│   ├── CAN_TX_RING
│   ├── ETH_TX_RING
│   ├── WIFI_TX_RING
│   ├── BT_TX_RING
│   ├── LTE_TX_RING
│   └── RS485_TX_RING
├── rx_pending_bitmap
├── tx_pending_bitmap
└── stats / event area
```

描述符字段建议：

| 字段               | 作用                                               |
| ------------------ | -------------------------------------------------- |
| `frame_id`         | Frame Pool 中完整 anyMSG 的 ID                     |
| `frame_offset`     | 完整 anyMSG 在 Frame Pool 中的偏移                 |
| `frame_length`     | 完整 anyMSG 字节数                                 |
| `source_interface` | 来源物理接口                                       |
| `target_interface` | 小核路由后写入的目标接口                           |
| `source_cid`       | 从 anyMSG 帧头提取的源地址                         |
| `destination_cid`  | 从 anyMSG 帧头提取的目的地址                       |
| `type`             | 从 anyMSG 帧头提取的 payload 类型                  |
| `priority`         | 内部调度优先级，默认普通优先级                     |
| `ttl`              | 内部转发 TTL，防止异常循环                         |
| `epoch`            | Linux 启动纪元，用于重启恢复                       |
| `crc16`            | 共享内存搬运校验                                   |
| `flags`            | 校验状态、是否分片重组完成、是否需要回执等内部标志 |

注意：

- priority 是共享内存描述符元数据，不写入 anyMSG 保留字段。
- Frame Pool 资源由 Linux 分配和最终释放；小核只移动描述符和更新消费状态。
- Ring 满时不覆盖旧描述符，必须丢弃新帧或按策略丢弃低优先级帧并记录统计。

## 9. 小核路由调度流程

小核核心任务链路：

```text
Mailbox ISR
  ↓
IPC Event Task
  ↓
读取 RX Pending Bitmap
  ↓
按预算 Drain 六路 RX Ring
  ↓
读取描述符并定位完整 anyMSG
  ↓
校验 msg_length / payload_length / CID / type / epoch / TTL
  ↓
type = 0x00 ?
  ├── 是：更新端在线表并消费帧
  └── 否：进入 Router Scheduler
          ↓
        根据 destination_cid 查询目标 TX Ring
          ↓
        按 priority 和防饥饿配额调度
          ↓
        TX Ring Writer 写目标 TX Ring
          ↓
        设置 TX Pending Bitmap
          ↓
        Mailbox Doorbell 通知 Linux
```

推荐优先级：

| priority | 含义              | 策略           |
| -------- | ----------------- | -------------- |
| `0`      | 紧急控制帧        | 最高优先级     |
| `1`      | 高优先级业务      | 优先于普通业务 |
| `2`      | 普通业务          | 默认值         |
| `3`      | 低优先级日志/状态 | 拥塞时优先丢弃 |

防饥饿策略采用“严格优先级 + 配额”：

```text
priority 0 : 每轮最多处理 16 帧
priority 1 : 每轮最多处理 12 帧
priority 2 : 每轮最多处理 8 帧
priority 3 : 每轮最多处理 4 帧
```

小核不直接操作 CAN 控制器，不处理 UART、SPI、网卡、蓝牙、4G 模块，也不解析 Modbus、UDS、J1939、CANopen 等复杂业务语义。

## 10. Mailbox 与 Pending Bitmap

Mailbox 只作为 Doorbell 使用，不承载任何完整数据帧。

Linux 写 RX Ring：

```text
1. 接入层重组出完整 anyMSG
2. Linux 分配 Frame Pool buffer 并写入完整 anyMSG
3. Linux 写对应物理接口 RX Ring 描述符
4. Linux 设置 rx_pending_bitmap 对应 bit
5. 如果该 RX Ring 从 empty 变为 non-empty，发送 Mailbox Doorbell 给小核
```

小核写 TX Ring：

```text
1. 小核完成路由和调度
2. 小核写目标物理接口 TX Ring 描述符
3. 小核设置 tx_pending_bitmap 对应 bit
4. 如果该 TX Ring 从 empty 变为 non-empty，发送 Mailbox Doorbell 给 Linux
```

Doorbell 丢失时，接收方必须通过周期 drain 兜底。Ring 和 Pending Bitmap 是唯一可信的数据状态来源。

## 11. Web 监控展示模块设计

Web 模块用于比赛演示、现场调试和系统运维查看，建议作为大核 Linux 上的独立轻量服务运行。后端使用 Rust + Axum/Tokio，前端使用 Vue3 / Vite。

Web 模块主要展示：

- CAN、以太网、Wi-Fi、蓝牙、4G、RS485、大小核通信的连通性；
- 每个接口的接收计数、发送计数、错误计数、最近通信时间；
- 接入层分片重组错误、共享内存队列状态、小核路由丢弃原因；
- CPU 使用率、内存占用、磁盘空间、网络收发速率、系统运行时间；
- 大核应用日志、协议适配器日志、IPC 异常日志、系统启动日志；
- 关键异常告警，例如模块断连、长时间无数据、CRC 错误、IPC 超时等。

Web 后端建议提供只读接口：

```text
GET /api/health       # Web 服务健康状态
GET /api/modules      # 各接口模块连通性和收发统计
GET /api/resources    # CPU/内存/磁盘/网络占用
GET /api/ipc-status   # 大小核通信和共享内存状态
GET /api/route-status # 小核路由、队列和丢弃统计
GET /api/logs         # 系统日志查询
GET /api/events       # 最近异常事件
```

Web 只读 Linux 生成的 `/run/put/status/` 快照和 `/var/log/put/` 日志，不直接访问共享内存，不向小核发送控制命令。

## 13. 异常处理与统计

必须记录以下统计，供 Web 或日志模块展示：

| 类别     | 统计项                                                                                |
| -------- | ------------------------------------------------------------------------------------- |
| 接入层   | rx bytes、rx frames、decode error、fragment drop、reassemble timeout、crc error       |
| 共享内存 | frame pool used、frame pool full、rx ring full、tx ring full、descriptor crc error    |
| 小核路由 | routed frames、heartbeat consumed、no route、ttl expired、invalid cid、invalid length |
| 出口层   | tx bytes、tx frames、fragment tx count、send fail、interface offline                  |
| Mailbox  | rx doorbell count、tx doorbell count、notify fail、periodic drain count               |

异常处理规则：

1. 非法 anyMSG 不进入小核调度队列。
2. 无路由帧不写 TX Ring，记录 no route。
3. TTL 过期帧立即丢弃。
4. Frame Pool 耗尽时优先保护高优先级控制帧。
5. 接口离线时不阻塞小核路由任务。
6. 所有丢弃必须有明确原因计数。

## 14. 与旧 v1 方案的关系

现有代码和部分文档中的 v1 方案具有以下特征：

```text
Linux 协议适配层
  ↓
96B unified_frame_t
  ↓
128B shared memory slot payload
  ↓
历史小核 CAN 输出路径
```

该方案适合早期 CAN direct 原型，但不适合作为 anyMSG 网关目标架构，原因是：

1. `unified_frame_t` 固定 96B，无法表达完整 anyMSG 的可变 payload。
2. 128B IPC payload 不能承载大于 128B 的 anyMSG。
3. v1 流程默认小核直接处理 CAN，不符合当前 CAN 也由 Linux 统一物理收发的边界。
4. v1 以 CAN 字段为中心，不能自然支持六类物理接口之间的统一路由。

迁移方向：

```text
v1: fixed slot payload + unified_frame_t
  ↓
v2: Frame Pool + Descriptor Ring + complete anyMSG
```

## 15. 测试计划

### 15.1 anyMSG 基础测试

- `msg_length == 40 + payload_length`；
- payload 长度为 0、最小值、最大值；
- CID 地址段解析；
- `type = 0x00` 心跳由小核消费；
- 非法长度、非法地址段、保留 type 的处理。

### 15.2 分片重组测试

- 每个低 MTU 接口完成分片发送与重组；
- 乱序分片；
- 丢片超时；
- 重复片；
- 分片 CRC 错误；
- `total_len` 超上限；
- 重组缓存耗尽。

### 15.3 共享内存测试

- 六路 RX Ring 和六路 TX Ring；
- Pending Bitmap 设置与清除；
- empty 到 non-empty 触发 Mailbox；
- Ring 满；
- Frame Pool 耗尽；
- 描述符 CRC 错误；
- Linux epoch 变化后的恢复。

### 15.4 路由调度测试

- CAN、以太网、Wi-Fi、蓝牙、4G、RS485 地址段路由；
- 无路由丢弃；
- priority 0/1/2/3 顺序；
- 防饥饿配额；
- TTL 过期；
- 目标接口离线。

### 15.5 集成测试

- 任一入口收到 anyMSG 后进入共享内存；
- 小核按 `destination_cid` 路由到目标出口；
- Linux 出口层读取 TX Ring 并真实发送；
- CAN 入口和出口同样走 Linux 物理收发路径；
- Web 或日志能看到每个接口的收发、路由、丢弃和错误统计。

## 18. 最终职责划分总结

```text
docs/              给老师、队友、答辩看的文档
common/            大核小核都要用的公共协议和 ABI
linux_app/         大核 Linux 真实物理收发和协议适配
web/               Web 监控展示模块
rtos_firmware/     小核 FreeRTOS 共享内存路由调度
c51_low_power/     C51 低功耗唤醒程序
tools/             调试工具
scripts/           构建、烧录、打包脚本
tests/             测试代码
third_party/       第三方库
```

一句话总结：

```text
Linux 负责真实物理收发、协议差异和分片重组；
小核负责共享内存中的完整 anyMSG 路由、队列调度和实时控制。
```
